## 1. 总体结构

```
SOP 文本 + 初始板位
      │
Agent 层            LangChain Agent（单个），LangGraph 保存全部对话和工具调用
      │ tool call
工具层（技能）      agent_tools/：每个工具是一个 Python 函数，Agent 只能看到这一层
      │ 函数调用（同一进程）
Lab Gateway        gateway/：状态表、互锁检查、执行器、MQTT 客户端、操作日志
      │ MQTT  192.168.1.20:1883，主题根 lab/v1
厂商网关 GW_001     厂商程序，运行在实验岛控制电脑上，逐条转发给驱动
      │ 串口 / 网线
设备                PCR002、T002001、TYPE_ROBOT_ARM001、STEERING_PLATFORM001、T006001
```

### 1.1 已定下的决策

| 决策 | 内容 | 与白皮书的关系 |
|---|---|---|
| Gateway 由我们实现 | 厂商只提供底层 MQTT 接口，组合、互锁、记录都在我们的 `gateway/` 里 | 白皮书原设定由设备团队部署 Gateway，改为我方 |
| 跨设备互锁由我们负责 | 厂商这一层的设备互相不知道对方存在，所以互锁写在 `wetlab/lab/interlocks.py` 里；物理急停仍由现场负责 | 白皮书原设定由现场 Runtime 负责互锁，改为我方 |
| Gateway 和 Agent 在同一进程 | Gateway 是 Python 包，工具函数直接调用，不加 HTTP 层 | 白皮书的独立 Gateway 服务，等出现第 1.2 节的条件时再拆 |
| Agent 只能调用技能 | 开门、抬热盖、夹紧这类底层指令不直接暴露给模型，由技能按固定顺序组合 | 白皮书 2.1 节的“技能封装” |
| 只用设备允许清单里的功能 | 不在 `ALLOW` 里的功能一律不发，包括所有直接坐标运动和改配置的功能 | 新增 |
| 一次只执行一个动作 | 厂商 GW_001 本身逐条处理，我们也不并发发送动作指令 | 白皮书的排程与并行留到后续 |
| 不需要人工确认 | Agent 的动作不经人工逐步审批（用户决定）；异常时自动冻结、等人处理 | 白皮书的人工审批改为异常冻结 |
| 暂不做 | Temporal、NATS、Virtual Lab、多 Agent、评测服务、模型训练 | 白皮书后续阶段 |

### 1.2 什么时候把 Gateway 拆成独立服务

出现下面任何一条时，给 `gateway/` 外面包一层 FastAPI，工具函数改成发 HTTP 请求，`gateway/` 内部不变：

- Agent 和实验岛不在同一个局域网；
- 有多个 Agent 进程同时使用实验岛；
- Agent 进程重启时，正在进行的设备动作仍需要有程序持续盯着。

## 2. 标识

| 标识 | 含义 | 格式 | 由谁生成 |
|---|---|---|---|
| `mission_id` | 一项研究任务 | `M-20261117-001` | 我们 |
| `experiment_id` | 一次实验，即一次 SOP 执行；也是 LangGraph 的 thread_id | `E-20261117-001` | 我们 |
| `operation_id` | 一条发给设备的指令；同时作为 MQTT 的 requestId | `WL-<毫秒时间戳>` | Gateway |
| `labware_id` | 一块板或一个容器 | `LW-001` | 实验开始时登记 |
| `position` | 我们给物理位置起的名字，例如 `rack:1-3`、`pcr`、`shaker`、`turntable` | 见 6.4 | 我们；对应厂商的点位编号见 9 节第 2 项 |
| `artifact_id` | 仪器产生的数据文件 | 待定 | 厂商的下机文件上报尚未实现 |

厂商调度系统的 requestId 前缀是 `S-`、`X-`，我们固定用 `WL-`，日志里可以直接区分。

## 3. 我们和厂商网关之间（MQTT）

这一节是 `gateway/` 里 MQTT 客户端必须遵守的规则。全部经过实测，和厂商文档不一致的地方以实测为准。

### 3.1 连接

| 项目 | 值 |
|---|---|
| 地址 | 192.168.1.20:1883，TCP，无 TLS |
| 账号 | admin（密码不写入代码，从环境变量读取） |
| 主题根 | `lab/v1` |
| 网关编码 | `GW_001` |
| 订阅权限 | `#` 被拒绝，`lab/v1/#` 允许 |
| 本机接入 | 网卡“Lab LAN”，192.168.1.99/24，不设路由器；上网走 Wi-Fi |

### 3.2 订阅

| 主题 | 用途 |
|---|---|
| `lab/v1/gateway/GW_001/telemetry` | 网关心跳，约每 3 秒一次。超过 10 秒没收到就认为网关离线 |
| `lab/v1/devices/{设备}/telemetry` | 设备状态，约每 3 秒一帧，**只包含有变化的属性**，需要按属性合并 |
| `lab/v1/devices/{设备}/status` | 上线 / 下线。异常断网时不一定会发，不能依赖 |
| `lab/v1/devices/{设备}/rpc/response/{operation_id}` | 指令的回执和结果 |
| `lab/v1/devices/{设备}/rpc/progress/{operation_id}` | 进度 |
| `lab/v1/gateway/GW_001/motion/response/{operation_id}`、`.../motion/progress/{operation_id}` | 机械臂搬运的结果和进度 |

### 3.3 发送

主题：`lab/v1/devices/{设备}/rpc/request/{operation_id}`，**QoS 0、不保留、只发一次、永不重发**。

```json
{
  "MsgId": "<uuid>",
  "Timestamp": 1794909921160,
  "GatewayCode": "GW_001",
  "DeviceCode": "T002001",
  "Type": "SetClamp",
  "Body": {
    "msgId": "<同上>",
    "requestId": "WL-1794909921160",
    "ts": 1794909921160,
    "deviceCode": "T002001",
    "action": "SetClamp",
    "timeout": 90,
    "SetClamp": {"clamp": true}
  }
}
```

主题里的设备编码必须和 `DeviceCode` 一致，主题最后一段必须和 `Body.requestId` 一致，`Type` 必须和 `Body.action` 一致，参数对象的键名等于动作名。格式不对时网关只记日志、不回任何消息。

### 3.4 判断结果

1. **忽略所有“已收到”回执（`Type=rpc-response`）。** GW_001、GW_002、GW_005 三个网关都会对任何设备指令回“已收到”，没有意义。
2. **只认 `GatewayCode=GW_001` 的 `Type=rpc-result`。**
3. **不看外层 `Body.Data.success`**，它几乎恒为 true（驱动报“未知功能”“找不到设备”时也是 true）。真实结果按设备取：

| 设备 | 真实结果字段 |
|---|---|
| PCR002 | `Body.Data.deviceData.success` |
| T002001 | `Body.Data.deviceData.ok`；`GetStatus` 直接返回状态字段 |
| TYPE_ROBOT_ARM001（MovMulti） | `motion/response` 上的 `Body.code == "0"` |
| TYPE_ROBOT_ARM001（只读查询） | `Body.Data.deviceData.success`（2026-11-18 实测） |
| STEERING_PLATFORM001 | `Body.Data.deviceData.success`；失败时 `deviceData.error` 是原因。**报失败不等于没动**：2026-11-18 两次报“未收到电机应答”，转向台实际都转到了位（现场目视确认） |
| T006001 | `deviceData` 里没有 success/ok 字段，只能看外层 `Body.Data.success`（2026-11-18 实测） |
| 网关异常分支 | `Body.code`，"0" 成功、非 "0" 失败 |

4. **拿到结果后，还要用遥测核对实际状态**（见 4.3）。驱动说成功不算数，设备状态变了才算。

### 3.5 已知行为（全部实测）

| 行为 | 对我们的影响 |
|---|---|
| GW_001 一次只处理一条指令，期间来的指令排队，前一条完成后才执行 | 不能并发；超时不代表没执行，可能还在排队 |
| 机械臂搬运、PCR 开关门、振荡定时等指令，要等物理动作结束才返回 | 期间任何指令（包括停止）都到不了设备，急停只能靠物理按钮 |
| 网关电脑的时钟比本机慢约 20 秒（2026-11-18 实测 22.7 秒，一个多小时内不变） | 先后顺序和超时一律用本机接收时间 |
| 设备遥测里的属性是驱动定时查询后缓存、每 3 秒发一次的。**指令结果返回后的第一帧可能还是旧值**：2026-11-18 振荡 `StopShake` 返回后第一帧仍是 46 rpm、夹紧，第二帧才是 0 rpm、松开；转向台返回“已到 89°”后第一帧仍是 0°。`WorkingStatus` 由网关维护，第一帧就是新的 | 核对指令结果要等状态和预期一致，不能拿第一帧下结论 |
| 有的设备报失败却照样执行了动作（2026-11-18 转向台，两次） | 会运动的设备报失败时，不能当作“没动” |
| 现场调试或重启网关时，GW_001 会整体停顿 10～155 秒：心跳和所有设备遥测一起停，期间指令收不到结果；重启后各设备重新发“上线”，`WorkingStatus` 归零（2026-11-18 上午 10 次） | 心跳超时按掉线冻结；使用实验岛的时间要和厂商约好，期间不改网关 |
| 网关上的设备登记会变：2026-11-18 01:36 华大 P8（`T009001`）被加到 GW_001；上午改配置时短暂出现过编码为 `4` 的“转向台” | 启动时用 `GetDevices` 核对设备清单 |
| 设备也可能被网关以外的方式操作（现场手动、本地软件），没有 MQTT 指令 | 状态以遥测为准，不能只靠自己的指令记录 |
| `GetProperty` 不可用；`GetDevices`、`GetDrivers` 可用 | 设备和功能清单用后两个刷新 |
| 一条指令失败后，该设备遥测 `WorkingStatus` 变为 2，下一条成功的指令（包括只读查询）后恢复为 0；网关重启也会清掉 | 互锁看到 2 会拒绝动作；先发一条只读查询确认设备正常。转向台没有只读功能，清不掉 |
| 设备主题不含网关编码，谁注册了这个设备编码谁执行 | 报文里的 `GatewayCode` 只是标签 |

### 3.6 绝不发送

`SyncLocation`（会整体覆盖示教点位）、`RegisterDevice`、驱动安装、以及任何不在 `wetlab/lab/interlocks.py` 的 `ALLOW` 里的功能。

## 4. Lab Gateway 内部规则

### 4.1 状态表

Gateway 启动后持续订阅遥测，维护：

| 内容 | 来源 |
|---|---|
| 每台设备每个属性的最新值，以及收到的时间（`_age_s`） | 设备遥测 |
| GW_001 是否在线 | 网关心跳 |
| 每块板在哪个位置 | **我们自己记录**：实验开始时登记，每次搬运成功后更新。料架没有传感器 |
| 是否冻结 | 见 4.4 |

### 4.2 一条指令的执行流程

```
1. 互锁检查 interlocks.check(设备, 动作, 参数, 状态表)  → 不通过：不发送，返回 BLOCKED
2. 确认没有别的动作指令在执行                         → 有：等待（我们自己也逐条执行）
3. 发送一次（QoS 0）
4. 等 GW_001 的最终结果，超时时间 = 该功能的预计时长 + 余量
      超时             → 记为 UNKNOWN，冻结
      结果为失败       → 记为 FAILED，把设备给出的原因原样返回
5. 用遥测核对动作后的状态（见 4.3）
      对不上           → 记为 VERIFY_FAILED，冻结
6. 记为 SUCCEEDED，写入操作日志
```

只读指令跳过第 1 步的状态检查、第 2 步和第 5 步。

### 4.3 动作后必须核对的状态

| 动作 | 核对内容（遥测） | 时限 |
|---|---|---|
| PCR `OpenDoor` | `DoorState=Open` | 10 秒 |
| PCR `CloseDoor` | `DoorState=Closed`；如果板在里面，`LidMotorState=Pressed` | 10 秒 / 15 秒 |
| PCR `SetLidMotor Lift` | `LidMotorState=Lifted` | 15 秒 |
| PCR `RunFile` | 结束后 `PcrState=Idle` | 程序时长 + 余量 |
| 振荡 `SetClamp true/false` | `ElmState=1` / `ElmState=2` | 5 秒 |
| 振荡 `StartShakeTimed` | 结束后 `ActualSpeed=0`、`ShakeState=1`、`ElmState=2` | 振荡时长 + 20 秒 |
| 机械臂 `MovMulti` | `RobotMode=使能空闲`、`SafetyStatus=NORMAL`；板位记录更新 | 90 秒 |

### 4.4 冻结

出现 `UNKNOWN` 或 `VERIFY_FAILED`，或者 GW_001 心跳中断时，Gateway 进入冻结状态：

- 拒绝所有动作指令，只读查询照常；
- 工具返回 `FROZEN`，Agent 停止实验并报告；
- 只有人到现场核对之后，调用 `gateway.unfreeze(原因)` 才能解除。原因会写入日志。

### 4.5 互锁规则（已实现：`wetlab/lab/interlocks.py`）

| 设备 | 规则 | 来源 |
|---|---|---|
| 所有设备 | 只发允许清单里的功能 | 安全原则 |
| 所有设备 | 动作前必须有 10 秒内的遥测；设备 WorkingStatus=2（故障）或 1（忙）时不发新动作 | 实测 |
| PCR | 启动任何加热程序前：门已关闭、热盖已压下、空闲 | **用户规定** |
| PCR | 自定义程序必须符合官方限制：≤30 步、A/C 区 4～99℃、梯度差 ≤36℃、保持 1～3600 秒、循环 1～99、只能往前跳、不能嵌套、速率 0～4℃/秒 | 官方属性文档 Rev 5 |
| PCR | 触摸屏锁定（InterfaceLock=1）时不发动作。=2 表示网关这一侧（485）掌握控制权，可以发 | 官方属性文档 Rev 5；2026-11-18 网关重启后实测出现 2 |
| PCR | 开门前热盖必须已抬起，且空闲 | 实测 |
| PCR | 关门必须带 `WaitLid=false` | 实测 |
| PCR | 热盖动作必须显式写 Lift 或 Press（默认值是封膜）；运行中不许抬热盖；门开着不许压热盖 | 实测 + 驱动说明 |
| 振荡 | 振荡前必须夹紧；转速 200～3000 rpm；温度 −10～120℃；振荡中不许松夹 | 设备配置 + 实测 |
| 机械臂 | 只能用 MovMulti，且所有点位必须在已确认的点位表里（目前为空，所以封锁）；必须使能空闲、安全状态正常、夹爪已连接 | 安全原则 |
| 转向台 | 机械臂运动时不许旋转；实测前只允许 0/90/180/270 度 | 安全原则 |

新增规则写进 `wetlab/lab/interlocks.py`，并在 `tests/lab/test_interlocks.py` 里加测试用例。

### 4.6 操作日志

每条指令一行 JSON，写入 `runs/{experiment_id}/operations.jsonl`：

```json
{"operation_id": "WL-1794909925567", "experiment_id": "E-20261117-001", "tool_call_id": "call_abc",
 "device": "T002001", "action": "StartShakeTimed", "params": {"seconds": 5},
 "interlock": "ok", "sent_at": "2026-11-17T18:05:25.567+08:00", "result_at": "2026-11-17T18:05:34.1+08:00",
 "status": "SUCCEEDED", "device_result": {"ok": true, "finished": true},
 "verify": {"ActualSpeed": 0, "ShakeState": 1, "ElmState": 2}, "error": null}
```

另外保留 MQTT 原始录制（`captures/`），用于事后排查。

## 5. Agent 能用的工具

### 5.1 所有工具的返回格式

```json
{
  "ok": true,
  "status": "succeeded",
  "result": {},
  "error": null,
  "operation_ids": ["WL-1794909921160", "WL-1794909925439", "WL-1794909925567"],
  "state_after": {"T002001": {"ShakeState": 1, "ElmState": 2, "ActualSpeed": 0}},
  "elapsed_s": 9.4
}
```

| `status` | 含义 | Agent 应该怎么做 |
|---|---|---|
| `succeeded` | 完成，状态已核对 | 继续 |
| `blocked` | 互锁不允许，什么都没发 | 读 `error.message`，调整顺序或参数后再试 |
| `failed` | 设备明确报告失败 | 读原因；可恢复的可以换做法，不可恢复的停止实验 |
| `unknown` | 发出后没等到结果，或结果与实际状态不符，Gateway 已冻结 | **不要重试**，停止实验并报告 |
| `frozen` | Gateway 处于冻结状态 | 停止实验并报告 |
| `not_available` | 这个工具还在等厂商资料或实测 | 不要使用，在报告里说明 |

### 5.2 错误码（`error.code`）

| 错误码 | 含义 |
|---|---|
| `INTERLOCK_BLOCKED` | 互锁检查不通过 |
| `INVALID_ARGUMENT` | 参数超出范围或格式不对 |
| `DEVICE_FAILED` | 设备报告失败 |
| `TIMEOUT_UNKNOWN` | 超时，动作可能还会执行 |
| `VERIFY_FAILED` | 设备说成功，但状态对不上 |
| `GATEWAY_OFFLINE` | GW_001 心跳中断 |
| `FROZEN` | Gateway 已冻结 |
| `NOT_AVAILABLE` | 工具尚未开放 |

### 5.3 工具清单

| 工具 | 作用 | 内部步骤 | 网关占用 | 状态 |
|---|---|---|---|---|
| `get_lab_state()` | 所有设备的关键状态、网关是否在线、是否冻结、每块板的位置 | 读状态表 | 无 | **可开发** |
| `pcr_open()` | 打开 PCR 仓门 | 热盖若压下则 Lift → 核对 → OpenDoor → 核对 | 约 10 秒 | **可开发**（已实测） |
| `pcr_close(plate_inside)` | 关闭 PCR 仓门 | CloseDoor(WaitLid=false) → 核对门；若有板，等热盖压下 | 约 5 秒 | **可开发**（已实测） |
| `pcr_list_programs()` | 列出 PCR 里存的程序 | ListFiles | 不到 1 秒 | **可开发**（已实测） |
| `pcr_run_program(name)` | 运行 PCR 里存的程序 | 检查门关+热盖压下+空闲 → RunFile → 等到 Idle | **整个程序时长** | 可开发，**首次需现场陪同实测** |
| `pcr_run_custom_program(steps)` | 运行自定义温度程序 | 检查门关+热盖压下+空闲+程序合规 → RunProgram（立即返回）→ 从遥测读进度直到 Idle | 不占用 | 可开发，**首次需现场陪同实测** |
| `shake(seconds, rpm)` | 夹紧后定时振荡，结束自动松夹 | SetClamp(true) → 核对 → SetTargetSpeed → StartShakeTimed → 核对 | 振荡时长 + 约 4 秒 | **可开发**（已实测） |
| `transfer(labware_id, to_position)` | 机械臂把板搬到另一个位置 | 查板位 → MovMulti（点位来自点位表）→ 核对 → 更新板位 | 约 40 秒 | `not_available`（缺点位表） |
| `rotate_turntable(angle)` | 转向台转到指定角度 | SingleLoop | 未知 | `not_available`（未实测） |
| `wait(seconds)` | Agent 等待一段时间（孵育等） | 本地计时 | 无 | **可开发** |

参数范围：

| 工具 | 参数 | 范围 |
|---|---|---|
| `shake` | `seconds` | 1～600（MVP 限制：更长的振荡会长时间占住网关，后续改用开始/停止两步） |
| `shake` | `rpm` | 200～3000 |
| `pcr_close` | `plate_inside` | true / false |
| `pcr_run_program` | `name` | 必须是 `pcr_list_programs()` 返回的名字之一 |
| `wait` | `seconds` | 1～3600 |

### 5.4 Agent 看不到的东西

MQTT、设备编码之外的任何厂商字段、底层指令（开门、抬热盖、夹紧、直接坐标运动）、点位编号。Agent 只看到 5.3 的工具名、说明、参数和返回值。

## 6. Agent 层

| 项目 | 规定 |
|---|---|
| 框架 | LangChain 创建 Agent，工具用普通 Python 函数定义；具体函数名以实现时的官方文档为准 |
| 记录 | LangGraph checkpointer（SQLite），`thread_id = experiment_id`，保存每条消息和每次工具调用，作为实验记录和以后的训练轨迹 |
| 模型 | 任何 OpenAI 兼容接口（DeepSeek、GLM、通义、Kimi 等）。通过配置 `LLM_BASE_URL`、`LLM_API_KEY`、`LLM_MODEL` 切换，代码不改。要求模型支持工具调用；不依赖并行工具调用和严格 JSON Schema 等各家支持不一的特性，工具层自己保证一次只执行一个动作 |
| 输入 | SOP 文本 + 初始板位登记（例如 `LW-001 在 rack:1-3`） |
| 输出 | 实验报告：执行了哪些步骤、每步结果、异常、最终状态 |
| 系统提示词必须包含 | 只能用给定工具；`unknown`、`frozen` 时立即停止，不许重试；不许猜测设备状态，需要时先调用 `get_lab_state()`；每一步说明理由 |
| 人工确认 | 不需要（用户决定） |
| 运行环境 | Python 3.11（系统自带 3.9 太旧），用 uv 管理依赖 |

### 6.1 一次运行的样子

```
输入：SOP“把 PCR 打开，确认里面的板，关门；然后振荡 10 秒 300 rpm”，初始板位：LW-001 在 pcr
Agent → get_lab_state()          PCR 门关、热盖压下、空闲；振荡模组空闲
Agent → pcr_open()               succeeded，门已打开
Agent → pcr_close(plate_inside=true)   succeeded，门已关闭，热盖已压下
Agent → shake(seconds=10, rpm=300)     succeeded
Agent → 输出实验报告
```

## 10. 下一步开发顺序
