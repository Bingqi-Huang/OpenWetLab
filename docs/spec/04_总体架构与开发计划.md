### 0.2 不能做的事

| 规定 | 原因 |
|---|---|
| 没有用户明确同意，不向真实设备发任何指令，不启动长时间的 MQTT 监听 | 实验岛和厂商人员共用，之前影响过他们 |
| 永远不发 `SyncLocation`、`RegisterDevice`、驱动安装，以及任何不在允许清单里的功能 | 01 第 3.6 节 |
| 运动指令只发一次，不重发；没等到结果就冻结 | 厂商网关会排队，重发会让设备动两次 |
| 真实设备上的动作只经过“提交方案 → 人批准 → 服务执行”这一条路，不写临时脚本直接发指令 | 第 5.15 节 |
| 只有服务进程向设备发指令。Agent 和界面不连 MQTT | 第 4 节 |
| 不做临时性的东西：不写“先简化、以后再换”的版本；每一块做出来就是正式版，带测试 | 用户的核心要求 |
| 不按假设开发：还没摸底的设备（华大 P8）不写代码 | 同上，避免返工 |
| MQTT 密码和模型 key 只从 `.env` 读，不写进代码和文档 | |
| 不要在用户没要求时提交 git commit | |
| 洗板机（GW_005）不在范围内 | 用户决定 |
| 虚拟岛和真机各用各的数据库文件，不混用；库里记着自己属于哪种岛，对不上就拒绝启动 | 第 5.13 节。否则虚拟岛上批准的方案会在真设备上接着执行 |
| 改界面的会话只改 `wetlab/app/`。`wetlab/lab/` 里它只能动各设备 `spec.py` 的显示名 | 界面只读数据库、只写命令；实验岛的逻辑不因为界面而改 |

## 1. 目标和范围

### 1.1 最终要做成的三样东西

| 产品 | 是什么 | 谁用 |
|---|---|---|
| **实验岛（Lab）** | 一套工具接口，背后是真实设备或虚拟设备。带互锁、物料记账、操作记录 | Agent（我们的和别人的） |
| **参考 Agent 系统** | 一个主 Agent 加若干子 Agent，通过上面的工具做实验 | 生物研究人员 |
| **评测（Bench）** | 一批任务、打分程序、对比表。让不同模型、不同 Agent 系统在同一个实验岛上做同样的任务 | 模型厂商、研究者 |

用户的长期目标：把前两样当作基础设施，外面包一层做成类似 Agents' Last Exam 的评测。架构必须为此留出空间。

### 1.2 第一阶段做什么

**在真实实验岛上演示跑通一个任务。** 不开发评测。

演示的样子：研究人员在网页上写要求 → Agent 出方案 → 人看方案并点“执行” → 设备执行 → 过程中可暂停、可停止，服务重启不丢进度 → 出报告。

目标任务是 [docs/task.md](../task.md)（单样本 SynCom seq 文库制备）。它的主要操作是移液，需要华大 P8，只用现有设备做不了全程。所以分阶段：

| 里程碑 | 内容 | 用到的设备 |
|---|---|---|
| 真机任务一（步骤 8） | 手写方案，经批准后由服务执行 task.md 的温度部分：三段恒温加 23 个循环的 PCR 程序。板由人放，孔里装水。高温部分带热盖加热（第 5.8 节） | PCR、振荡 |
| 真机任务二（步骤 11） | 同样的任务，由 Agent 从文字要求开始做 | 同上 |
| 之后 | 机械臂搬运（搬运参数对齐后）；华大 P8 摸底和接入；task.md 全程 | 加机械臂、P8 |

**先做现有设备（PCR、振荡、机械臂、转向台、料架），华大 P8 等现场摸底之后再开发。**

### 1.3 最终用户

完全不写代码的生物研究人员。界面、报错、报告都用他们能直接看懂的中文。

### 1.4 开发原则（用户明确要求）

1. **不做临时性的东西。** 可以分先后，但每一块做出来就是正式版，以后不重写。依赖未知事实的部分，先查清再做。
2. **不写防御性代码。** 检查只放在规定的几处（第 12 节），其余代码不写兜底分支、不吞异常、不重试。
3. **能用成熟的库就不自己写。**
4. **不无理由加层次。** 加任何中间层前先说清必要性。
5. **可维护、可扩展、易读。** 一个文件只管一件事；按设备分文件夹；包之间单向依赖（第 5.2 节）。

### 2.1 AutoDNA（Nature 2026-11，源码 github.com/IPADS-X/AutoDNA）

论文正文需要登录，没有读到。以下来自源码仓库和报道。

| 方面 | 它的做法 | 我们取什么 |
|---|---|---|
| Agent 分工 | 6 个 Agent（文献、方案、试剂、代码、硬件、假设）作为**工具**挂在一个执行 Agent 下；最外层是普通 Python 写的规划器 | 子 Agent 当工具用；主流程不需要复杂的图 |
| 到硬件的路径 | Agent 生成步骤文件 `protocol_flow.json`，交给 C++ 调度器执行 | Agent 和设备之间有一份结构化的方案文件 |
| 执行前检查 | 生成的代码先在数字孪生里跑，检查液体体积、器皿位置 [间接] | 先在虚拟岛预演 |
| 失败处理 | DNA 存储实验 203 小时里 14 次硬件错误，6 次需要人 [间接] | 硬件错误需要人是常态，冻结加人工解除是对的 |
| 自己承认的问题 | 模型随机性影响方案可重复性；设备接口各异，难搬到别的实验室 [间接] | 方案文件存下来可原样重跑；设备差异关在后端和设备文件夹里 |
| 规模 | 20 多种仪器、连续 203 小时、上万步硬件操作，做了酶促 DNA 合成、DNA 存储读写、突变检测 [间接，审查提供] | 我们的实验岛在设备数量和实验规模上远小于它，不能在这上面比 |
| 没有的 | 公开资料里没有见到不同模型之间的对比评测 | 别的领域已经有人做了物理仪器上的多模型评测（第 2.4 节的 AILA），生物实验的评测基准也不少（第 2.5 节）。评测不是空白 |

### 2.2 Google Research 的 VERID（2026-10-16 博客，论文 arXiv 2610.32755 只读了摘要）

和接入 P8 最相关。它建在开源的 PyLabRobot 上，让 Agent 规划、仿真、执行移液流程。

| 它的经验 | 对我们的含义 |
|---|---|
| 大模型对三维几何和物理状态的推理不可靠 | 哪个孔里有多少液体、枪头还剩几个，必须由程序记账，模型去查 |
| 一条指令可能出三类问题：**物理上做不到**（8 通道移液头伸进太窄的槽）、**物料上不成立**（从已经吸空的孔里吸液）、**科学上有偏差**（贴着孔底排液造成分层、枪头挂壁残留） | 前两类靠仿真和检查拦住。第三类仿真拦不住，只能靠观测和完整的过程记录事后发现 |
| 四项能力：实时状态（台面布局、每孔体积、可用枪头）；几秒内完成的虚拟预演；硬件安全检查；同步的视频和动作日志 | 前三项我们的设计里已有对应。视频没有（第 7.4 节） |
| Agent 从不把未验证的代码直接发给移液机器人 | 和“先预演、人批准、再执行”一致 |
| 仿真拒绝某个操作后，Agent 当场改方案 | 预演的报错要写清第几步、为什么、当前状态 |
| 状态持久保存，读板机出故障后可以中途恢复，不用重新移液 | 物料账本在数据库里；失败后只重做剩余步骤 |
| 记录停留时间、蒸发、板布局这类过程变量 | 操作记录要能还原每块板在每个时刻的经历 |
| 案例都用染料和水；用俯视相机读颜色做闭环，准确度提高 5 倍以上 | 染料加相机可以最低成本地做出“根据结果调整下一轮”的闭环（第 7.5 节） |
| 未解决的问题：防止 Agent 走实验上的捷径 | 以后做评测时，打分要防捷径 |
| **同一篇博客里的另一项工作：适配体闭环**。Agent 反复设计、合成、筛选、测序适配体，测序结果直接回到 Agent。第一轮命中率 0%，Agent 从数据里找出原因并改设计，后两轮命中率明显上升。博客的原话：Agent 需要真实的实验读数来修正假设 | **VERID 只是他们的底座，体现科学价值的是有读数的闭环。** 我们的实验岛现在没有任何读数（第 7.5、15.2 节） |

### 2.3 自动化实验室软件框架（MADSci、AlabOS、PyLabRobot、SiLA 2 等）

| 它们共有的概念 | 我们对应的东西 |
|---|---|
| 设备 和 动作 分开 | 设备文件夹里的 `spec.py`；技能 |
| 物料 和 设备 分开，位置有“被谁占用” | 器皿账本 |

### 2.4 自主科研 Agent 系统

| 来源 | 结论 |
|---|---|
| Anthropic 多 Agent 研究系统 | 主 Agent 加并行子 Agent 比单 Agent 好 90%，但耗 token 约 15 倍。适合能并行的**只读**任务 |
| Cognition（2026-04） | 多 Agent 有效的前提：**写操作保持单线程**，多出来的 Agent 只提供判断不动手 |
| LangChain 官方文档 | 推荐的多 Agent 形式是“子 Agent 当工具” |
| AutoLabs（化学机器人） | 最后一步由规则代码而不是模型转成机器人指令。模型推理能力的影响大于单 Agent 还是多 Agent |
| AILA / AFMBench（Nature Communications 2025，原子力显微镜） | 在真实仪器上做了 100 个任务的基准，比较了多个模型，也比较了单 Agent 和多 Agent：摘要的结论是多 Agent 明显好于单 Agent，但两者都对提示词的细小改动敏感。它把 Agent 偏离指令、擅自多做步骤的现象叫“梦游” |
| AutoDNA | 也出现过模型擅自加步骤的情况 [间接] |

上一版这里写“没有找到在物理实验执行上直接比较单 Agent 和多 Agent 的证据”，是错的：AILA 就做了这个比较。

## 3. 已定的决定

| # | 决定 | 理由 |
|---|---|---|
| 1 | **实验岛是独立的一层，不引用任何大模型库** | 评测时被测对象可能是我们的 Agent 换模型，也可能是别人的整套系统 |
| 2 | **真实和虚拟只在后端不同**，上层代码完全共用，不出现“如果是虚拟”的判断 | 白皮书要求虚实同一套工具接口 |
| 3 | **实验岛 = 后端 + 数据库。** 真机是“MQTT 后端 + 文件数据库”，虚拟岛是“虚拟后端 + 文件数据库”，预演和测试是“虚拟后端 + 内存数据库” | 只有一条代码路径 |
| 4 | **按设备分文件夹。** 一台设备的说明、互锁规则、虚拟模型、技能放在一起 | 加一台设备等于加一个文件夹 |
| 5 | **两个 Agent：协调者和操作员。** 两者是各自独立的会话，通过数据库里的任务单、方案、结果交接，由事件唤醒。以后的角色同样加入，且只读 | 白皮书第 6 节。实验要等人批准、等设备执行，可能跨天；跨这种等待不能用“子 Agent 当同步工具”（第 6.1 节） |
| 6 | **Agent 和设备之间有一份方案**：一串技能调用，JSON | 可预演、可给人看、可重跑、可当评测的参考解 |
| 7 | **先批准再执行**：真机只执行人批准过的方案。Agent 不能直接让真实设备动，也不向真实设备发任何指令（包括只读查询） | 用户决定；所有设备通信只从服务一个进程发出 |
| 8 | **方案由程序执行，不经过模型**；Agent 只在规划和出现偏差时工作 | 可重复；等待期间不花模型费用 |
| 9 | **常驻的实验岛服务加 SQLite**，支持跨天跨周运行；服务随时可以重启。**不用 Temporal** | 用户决定：单个实验岛用这个就够 |
| 10 | **三个进程，共用一个数据库文件**：服务、Agent、界面。除服务外，谁都只读数据库、只往 `commands` 表写命令 | 模型调用很慢，不能占住控制设备的循环；实验岛状态只有一个写入者 |
| 11 | **占住厂商网关的技能不超过约 1 分钟**，长时间只出现在方案的“等待”步骤里 | 网关被占住期间停止指令到不了设备；等待可以存库、跨重启 |
| 12 | **随时可暂停、可全部停止**，并如实说明厂商网关造成的限制 | 用户要求 |
| 13 | **物料由程序记账，模型去查** | VERID 的经验；料架没有传感器 |
| 14 | **出问题只有三种反应**：拦下、把原因交给 Agent、冻结等人。设备指令不重试 | 01 的实测结论 |
| 15 | 用 `create_agent` 加官方中间件，不用 deepagents；模型用 `init_chat_model` 按配置建 | 成熟度；用户要求模型可换 |
| 16 | 给研究人员的是网页，给开发的是命令行，不加 HTTP 层 | 用户不要多余的层 |
| 17 | **先做现有设备，P8 摸底后再开发** | 用户决定 |
| 18 | 第一次真机加热任务用手写方案，不经过 Agent | 不把设备的不确定和模型的不确定混在一起 |
| 19 | 评测第一阶段不开发，只保证现在的结构以后能接上 | 用户决定 |
| 20 | PCR 的热盖加热、板容量、模式三项设置加进允许清单，带规则（第 5.8 节） | 用户决定（2026-11-18）。不开热盖，高温下液体会蒸到盖上 |
| 21 | 实验读数（测量）是以后要做的事，现在只记录；评测用单座真机可以接受 | 用户决定（2026-11-18），见第 15.2 节 |
| 22 | **冻结时仍然允许停止类指令**（停程序、停振荡、关热盖）。任何一台设备没停成功，“全部停止”就如实报失败 | 冻结正是人最可能想停设备的时候；停止是往安全方向走（第 5.5、5.14 节） |
| 23 | **虚拟岛和真机各用一个数据库文件，库里记录自己属于哪种岛**，启动时对不上就拒绝 | 否则虚拟岛上登记的器皿、批准过的方案会被真机当真（第 5.13 节） |
| 24 | **未开放的技能在提交和批准时就拦下**，不等执行到那一步 | 否则前面的步骤已经让真设备动了，方案才失败（第 5.8、5.9 节） |
| 25 | **互锁和核对只用比上一条指令的结果更新的状态** | 设备约 3 秒上报一次状态，指令返回后“忙”的标记要晚 1～3 秒才清（第 5.5 节） |
| 26 | **报告的事实部分只由服务生成**，Agent 只提供结论文字 | 事实来自数据库，不应取决于 Agent 进程当时在不在（第 6.5 节） |

## 4. 总体结构

```
   界面进程（网页 / 命令行）            Agent 进程（wetlab agents）
   读数据库；写 commands               读 events；跑协调者、操作员；写 commands
            │                                   │
            └──────────────┬────────────────────┘
                           ▼
        这座岛的数据库（runs/real/ 或 runs/virtual/ 下的 wetlab.sqlite）
                           ▲
                           │ 唯一写入实验岛状态的进程
┌─ 服务进程（wetlab serve）──────────────────────────────────────────┐
│  service   读命令 → 推进已批准的方案 → 检查等待 → 写事件 → 通知      │
│  protocol  方案：校验、执行一步、预演、生成给人看的文本               │
│  registry  技能的登记和调用                                         │
│  lab       发指令的唯一入口：冻结 → 互锁 → 发送 → 核对 → 记录         │
│  devices   每台设备一个文件夹：说明、规则、虚拟模型、技能             │
│  store     数据库（SQLite）                                         │
│  ─────────────── 后端接口 ───────────────                          │
│  mqtt  真实后端（GW_001）              sim  虚拟后端                 │
└───────────────────────────────────────────────────────────────────┘
```

四条总规则：

1. `lab` 不引用 `agents`、`app`，也不引用任何大模型库。
2. 只有服务进程持有后端、向设备发指令、写实验岛状态。Agent 和界面只读数据库、只写 `commands` 表。
3. 真实和虚拟的差别只存在于 `lab/mqtt/`、`lab/sim/` 和各设备的 `sim.py`。
4. 后端以上（技能、规则、方案、数据库、界面、Agent）一律用设备的短名（`pcr`、`shaker`、`arm`、`turntable`、`rack`）；厂商设备编码（`PCR002` 等）只出现在各设备的 `spec.py` 和后端里，由 `Lab` 转换。

## 5. 实验岛（lab）

### 5.1 概念

| 概念 | 是什么 | 例子 |
|---|---|---|
| 设备 | 一台仪器，有若干底层动作和一组状态属性 | `pcr`（厂商编码 `PCR002`）：动作 `OpenDoor`，属性 `DoorState` |
| 位置 | 能放器皿的地方，用名字表示。料架按槽位编码命名 | `rack:1-2`、`rack:1-3`、`pcr`、`shaker` |
| 器皿 | 一块板，有编号、类型、当前位置、经历 | `LW-001` |
| 技能 | 方案能调用的一个操作，带类型参数和统一返回格式 | `shake(seconds, rpm)` |
| 方案 | 一串技能调用和等待 | 第 5.9 节 |
| 操作 | 发给设备的一条底层指令的记录 | `WL-1794909925567-42` |
| 任务 / 实验 | 一项研究任务包含若干实验；一个实验对应一份方案的一次执行 | `M-20261118-001` / `E-001` |

规则：

| 规则 | 内容 |
|---|---|
| 文件大小 | 一个文件只管一件事。超过约 300 行就拆；内容相关的几张表放一个文件，不为了“一表一文件”拆碎 |
| 测试 | `tests/` 的目录和代码目录一一对应，如 `tests/lab/devices/pcr/test_sim.py` |
| 包之间的依赖（只能往下引用） | 从上到下五层：① `service` ② `protocol` ③ `registry`、`snapshot`、`sim`、`mqtt` ④ `lab.py`、`safety`、`materials` ⑤ `store`、`devices`、`backend`、`errors`。同一层里：`sim` 和 `mqtt` 互不引用；`snapshot` 只引用 `store` 和 `devices`；`sim`、`mqtt` 只引用 `devices`、`backend`、`errors` |
| 技能怎么登记而不成环 | `@skill` 装饰器定义在最底层的 `devices/base.py`，它只给函数贴上名字、说明、读还是动。各设备的 `skills.py` 只引用它。技能函数的第一个参数 `lab` 是调用时传进来的对象，`skills.py` 不引用 `lab.py`。上层的 `registry.py` 遍历 `ISLAND`，把各设备 `skills.py` 里贴了标记的函数收集起来 |
| 设备文件夹之间 | **互不引用。** 一台设备的规则需要另一台设备的状态时，从传进来的状态表里按短名取；需要调另一台设备的判定时，由上层（`safety.py`、`sim/world.py`）查到再调 |
| 检查方式 | 用 import-linter 把上面的依赖写成契约，随测试一起跑 |

### 5.3 设备文件夹

每个文件的内容以 PCR 为例。现有 `interlocks.py` 和 `layout.py` 的规则内容搬进来；状态表的键从厂商编码改成短名。

**spec.py：这台设备是什么**

```python
NAME = "pcr"                                  # 后端以上都用它
CODE = "PCR002"                               # 厂商编码，只有后端用
ACTIONS = {                                   # 不在这里的动作一律不允许
    "GetPcrStatus": Action(READ),
    "OpenDoor":     Action(ACT, seconds=5),   # seconds：占住网关的时长，用于缺省超时
    "RunProgram":   Action(ACT),
    ...
}
STATE_PROPS = ["DoorState", "LidMotorState", "PcrState", "FaultText"]   # 每帧遥测都有；缺了就当作看不见这台设备
KEY_PROPS = STATE_PROPS + ["PcrRemainingSeconds", "LidTemperature", "HeaterLidEnabled"]  # 给人和 Agent 看的
# 位置（示教点位）不写在这里，见第 5.16 节：由现场配置文件 island/GW_001/positions.json 给出

def result_ok(action, data) -> tuple[bool, str]:
    """从一条已经过了网关层检查的应答里，判断设备这次是成功还是失败。"""
```

`result_ok` 存在的原因：同一个网关上各设备报成功的方式不同（01 第 3.4 节，实测）：

| 设备 | 怎样算成功 |
|---|---|
| PCR | `deviceData.success`。外层的 `Data.success` 恒为 true，不看 |
| 振荡 | 动作看 `deviceData.ok`；`GetStatus` 直接返回状态字段 |
| 机械臂 `MovMulti` | 同一个请求会收到**两条**结果：先是设备主题上的一条（只有 `Data.success`，`deviceData` 为空），约 3 毫秒后是网关主题 `motion/response` 上的一条（带 `code`，`"0"` 成功）。只认 `motion/response` 那一条，设备主题上的那条忽略。抓包第 58/59 行（成功）、1458/1459 行（失败）是测试用例 |
| 转向台 | `deviceData.success`；**报失败不等于没动**（2026-11-18 实测，见第 16.6 节第 31 项） |
| 料架 | `deviceData` 里没有 success/ok，只看外层 `Data.success`（2026-11-18 实测） |

所以 `spec.py` 里除了 `result_ok`，还要声明每个动作的最终结果从哪个主题来（缺省是设备主题；机械臂的 `MovMulti` 是 `motion/response`）。

各设备 `KEY_PROPS` 要改正的地方（对照抓包）：

| 设备 | 改正 |
|---|---|
| 振荡 | 加 `BlockTemperature`、`TargetTemperature`、`TempControllerStateText`。实测它当前在 30℃ 制热，人和 Agent 必须看得到 |
| 转向台 | 属性名是 `Angles`，值是字符串（`"0"`、`"90"`），不是 `Angle` |
| 料架 | 属性名是小写开头的 `rackState`、`errorCode` |
| PCR | 加热盖温度和热盖加热开关 |

### 5.4 后端接口（backend.py）

```python
class Backend(Protocol):
    closed_skills: set[str]      # 这个实验岛上还没开放的技能
    def call(self, device_code, action, params, timeout_s, operation_id) -> dict:
        """发一条底层指令，等到最终结果。设备报失败抛 DeviceFailed，没等到结果抛 NoResult。
        operation_id 由 Lab 生成；真实后端把它用作报文的 requestId。"""
    def state(self) -> dict:
        """{厂商编码: {属性: 值, "_age_s": 距上次收到完整状态的秒数, "_error": 设备报错文本或 None},
            "_gateway": {"online": bool, "busy_by_others": bool}}"""

    def sleep(self, seconds)     # 让这个实验岛的时钟走过 seconds
```

系统里所有时间都取 `backend.now()`，所有等待都用 `backend.sleep()`。虚拟后端的 `sleep` 瞬间完成，所以测试里几小时的流程一秒内跑完，且结果确定。虚拟后端的 `_gateway` 恒为在线、不忙。

### 5.5 Lab（lab.py）

`Lab(backend, conn)`。`Lab.state()` 把后端状态表的键换成短名。`Lab.do(device, action, params, expect=None, within_s=15, timeout_s=None)` 是所有底层指令的唯一入口，实现 01 第 4.2 节的流程：

```
1. 已冻结，且不是只读、也不是停止类动作 → 抛 Frozen
2. safety.check 不过     → 记录，抛 Blocked（什么都没发）
3. 生成操作编号，backend.call（带上这个编号）
     NoResult            → 冻结，记录，抛 Unknown("TIMEOUT_UNKNOWN")
4. 等这台设备的一帧新状态：收到时刻不早于指令返回时刻的完整状态，最多等 10 秒
     动作类指令等不到   → 冻结，记录，抛 Unknown("VERIFY_FAILED")
     只读指令等不到     → 不处理，继续
   第 3 步是 DeviceFailed → 等完这一帧后记录，原样抛出
5. 有 expect 时，每秒读一次状态，within_s 内全部对上才算成功
     对不上              → 冻结，记录，抛 Unknown("VERIFY_FAILED")
6. 记录，返回设备结果
```

**为什么要等一帧新状态（第 4 步）**：设备约 3 秒上报一次状态。抓包 `test_session.jsonl` 里，振荡的只读查询在第 9.41 秒返回，状态到第 11.99 秒才从“忙”变回空闲；定时振荡在第 77.0 秒返回，第 78.0 秒才清。不等的话，紧接着的下一条指令会被我们自己刚结束的指令拦住（互锁第 4 条），`expect` 也可能拿指令返回前的旧状态去核对。虚拟后端的状态永远是最新的，这一步立即通过。

**2026-11-18 实测补充**：这一帧里只有 `WorkingStatus` 一定是新的（它由网关维护）；设备自己的属性是驱动定时查询后缓存的，**这一帧里仍可能是旧值**。例：振荡 `StopShake` 返回后的第一帧仍是 46 rpm、夹紧，下一帧才是 0 rpm、松开；转向台返回“已到 89°”后第一帧仍是 0°。所以第 4 步只能保证互锁第 4 条不误拦，设备属性的核对只能靠第 5 步的 `expect` 轮询到对上为止。改法见第 16.6 节第 32 项。

**停止类动作**：`safety.is_stop(device, action, params)` 判断。缺省看 `spec.py` 里该动作的 `stop=True`（`StopRun`、`PauseRun`、`StopShake`、机械臂的 `Stop` 等）；设备可以在 `rules.py` 里写 `is_stop(action, params)` 补充，PCR 用它把“关热盖加热”（`SetHeater{Zone:Lid, Enabled:false}`）也算进去。冻结时放行的和互锁第 4 条豁免的是同一批动作，只在这一个函数里定义。

| 细节 | 规定 |
|---|---|
| `timeout_s` 缺省值 | 该动作在 `spec.py` 里的 `seconds` 加 20 秒；没有登记的按 15 秒 |
| 操作编号 | `WL-<毫秒时间戳>-<序号>`。序号是这个数据库里操作记录的顺序号，所以同一个库里永不重复（虚拟岛的时钟可以重复，序号不会）。**发送之前生成，传给后端**；真实后端把它用作报文的 `requestId`，所以 `operations` 表、`freeze` 表里的编号能在 `raw/` 的原始报文里直接查到。后端自己不再另编一套编号 |
| 记录 | 写 `operations` 表 |
| 冻结 | 写 `freeze` 表：原因、引起它的操作编号。`Lab.unfreeze()` 只由服务在处理人的“解除冻结”命令时调用 |
| 异常 | `errors.py`：`DeviceFailed`、`NoResult`（后端抛）；`Blocked`、`Unknown`、`Frozen`（`Lab` 和账本抛）；`SkillFailed(code, message)`（技能自己检查出结果不对时抛，如程序提前结束） |
| 查上一次操作 | `Lab.last_operation(device, action)`：从 `operations` 表取这台设备这个动作最近一条成功记录（时间、参数）。技能用它知道“上次启动的是什么、什么时候启动的” |

### 5.6 互锁入口（safety.py）

`check(device, action, params, state) -> (ok, reason)`，按顺序：

```
1. 设备不在 ISLAND 里，或动作不在该设备的 ACTIONS 里          → 拒绝
2. 动作是只读                                               → 允许
3. 网关不在线（心跳超过 10 秒没收到）                         → 拒绝，GATEWAY_OFFLINE
4. 网关正被别人的指令占着，或岛上任一设备 WorkingStatus=1      → 拒绝（停止类动作除外）
5. 该设备超过 10 秒没收到完整状态，或缺 STATE_PROPS 里的属性   → 拒绝
6. 该设备带着报错（_error 非空），或 WorkingStatus=2          → 拒绝
7. 该设备的 rules.check                                     → 有原因就拒绝
8. 这是机械臂的搬运：对 positions_touched 里每个位置，
   找到位置所属的设备，调它的 ready_for_arm                   → 有原因就拒绝
```

第 3～6 条是现有 `interlocks.check` 没有覆盖的情况，都在抓包里出现过：

| 情况 | 抓包里的证据 | 不处理的后果 |
|---|---|---|
| 设备串口断开 | PCR 串口被占后，遥测只有一条 `error`，没有任何状态属性，但每 3 秒照发 | 状态表里留着断开前的旧值，看起来一切正常 |
| `WorkingStatus` 只在变化时上报 | PCR 的 197 帧遥测里它只出现 2 次 | 服务启动后读不到它，“忙”和“故障”都查不出来。所以放行依据是每帧都有的 `STATE_PROPS`，`WorkingStatus` 只作为补充 |
| `WorkingStatus` 的含义 | 抓包核实：1 = 正在执行指令（只读查询期间也是 1）；0 = 上一条指令成功；2 = 上一条指令失败。2 会一直留着，直到这台设备下一条指令成功（PCR：失败的 `GetProperty` 之后是 2，114 秒后一条成功的 `GetDoor` 才变回 0） | 设备失败一次后，它的所有动作都被第 6 条拦住。处理办法见第 5.14 节“某一步失败之后” |
| 状态比指令结果晚到 | `test_session.jsonl`：结果回来后 1～3 秒，状态里才清掉“忙” | 紧接着的下一条指令被第 4 条误拦。处理办法是 `Lab.do` 的第 4 步（第 5.5 节），不在这里放宽规则 |
| 别人也在给 GW_001 发指令 | 厂商调度系统的 `S-`、`X-` 开头的指令 | 网关逐条处理，我们的指令会排在后面超时，冻结后又被执行 |
| 网关掉线 | 2026-11-17 18:42 实际发生过 | 01 第 4.4 节规定要冻结 |

`kind(device, action)` 返回读还是动。`is_stop(device, action, params)` 返回是不是停止类动作（第 5.5 节）。

“设备带着报错”除了 `_error` 和 `WorkingStatus=2`，还包括设备自己的故障属性（PCR 的 `FaultText`、振荡的 `ErrorCode`）。这类判断写在各设备 `rules.py` 的 `fault(state) -> 原因或 None` 里，`safety.py` 和 `protocol/` 都调它；这两处的代码里不出现具体设备的名字。

### 5.7 器皿账本（materials.py）

数据在 `labware` 和 `labware_events` 两张表里。

| 函数 | 作用 |
|---|---|
| `where(labware_id)`、`at(position)` | 板在哪；位置上是哪块板 |
| `place(labware_id, type, position)` | 人把一块板放上岛。位置有板则抛 `Blocked` |
| `remove(labware_id)` | 人把板拿走 |
| `correct(labware_id, position)` | 人更正一块板的位置（账本和现场不一致时） |
| `move(labware_id, to_position, operation_id)` | 机械臂搬运成功后调用。目标位置有板则抛 `Blocked` |
| `record_at(position, what, **detail)` | 给某位置上的板记一条经历。位置上没板就不记 |
| `history(labware_id)` | 这块板的全部经历 |

`place`、`remove`、`correct` 由服务在处理对应命令时调用（第 5.14 节），每次都记一条经历，写明是人做的。

**板里装了什么（2026-11-18 用户决定加上）**：任务可能写成“把样品 X 做 PCR”，Agent 要能从账本查到样品 X 在哪块板上、那块板在哪。

| 项目 | 规定 |
|---|---|
| 表 | `labware_contents`：`labware_id`、`n`（行号）、`name`（样品或试剂名，如 `X`、`SynCom-1`、`PCR master mix`）、`wells`（孔位列表，如 `["A1","A2"]`；空表示整块板）、`volume_ul`（可空）、`note`（可空）。用新编号的迁移文件加 |
| 谁写 | 人：登记器皿时一起填，之后可以单独改（命令 `set_labware_contents`）。设备不改内容（PCR、振荡只改“经历”） |
| 谁读 | Agent 的 `get_lab_state` 返回每块板的位置、类型、内容；方案审阅页的“执行前现场应该是这样”列出涉及的板及其内容；报告的器皿经历里带上内容 |
| 函数 | `materials.set_contents(labware_id, items)`、`materials.contents(labware_id)`、`materials.find(name) -> [labware_id]` |
| 以后 | P8 接入后按第 7.3 节做到每个孔的体积和成分，在这张表的基础上扩展，不另起一套 |

料架有更多槽位（例如示教了最高层 `1-1`）时，只在现场配置里加一个位置（第 5.16 节），账本和表结构不变。

### 5.8 技能和注册表（registry.py）

技能是普通 Python 函数，直线写，不处理异常：

```python
@skill(kind="act", label="振荡 {seconds} 秒，{rpm} rpm")
def shake(lab, seconds: Annotated[int, Field(ge=1, le=60)],
               rpm: Annotated[int, Field(ge=200, le=3000)]):
    """Clamp the plate, shake for `seconds` at `rpm`, then release the clamp."""
    lab.do("shaker", "SetClamp", {"clamp": True}, expect={"ElmState": 1})
    lab.do("shaker", "SetTargetSpeed", {"rpm": rpm})
    lab.do("shaker", "StartShakeTimed", {"seconds": seconds},
           expect={"ActualSpeed": 0, "ShakeState": 1, "ElmState": 2}, timeout_s=seconds + 30)
    lab.materials.record_at("shaker", "shaken", seconds=seconds, rpm=rpm)
```

`registry.call(lab, name, **args)` 是调用技能的唯一入口，在**这一个地方**完成：

| 事情 | 做法 |
|---|---|
| 未开放 | `name in lab.backend.closed_skills` → 返回 `not_available` |
| 参数检查 | 用 pydantic 按函数签名校验，不过 → `blocked` / `INVALID_ARGUMENT` |
| 异常转返回值 | `Blocked`→`blocked`；`DeviceFailed`→`failed`，错误码 `DEVICE_FAILED`；`SkillFailed`→`failed`，错误码是技能给的（如 `PROGRAM_ENDED_EARLY`）；`Unknown`→`unknown`；`Frozen`→`frozen` |
| 统一返回格式 | 01 第 5.1 节：`ok, status, result, error{code,message}, operation_ids, state_after, elapsed_s`。`state_after` 只含各设备的 `KEY_PROPS` 和器皿位置 |

`registry.catalog()` 导出每个技能的名字、说明、参数及范围、读还是动、版本哈希。提示词里的工具说明、环境说明、以后的 MCP 工具都从它生成。

工具名和说明用英文（给模型看，也便于以后对外评测），`label` 是给人看的中文模板。

**`pcr_start_program` 的参数**

模型和人都按“阶段”写，循环是一个带次数的块，不填跳转步号：

```json
{"stages": [
   {"temperature_c": 98, "hold_seconds": 60},
   {"repeat": 23, "steps": [{"temperature_c": 98, "hold_seconds": 10},
                            {"temperature_c": 60, "hold_seconds": 5},
                            {"temperature_c": 72, "hold_seconds": 5}]},
   {"temperature_c": 72, "hold_seconds": 60}]}
```

| 规定 | 内容 |
|---|---|
| 范围 | `temperature_c` 4～99，`hold_seconds` 1～3600，`repeat` 2～99；块不能嵌套；展开后的设备步数不超过 30 |
| 技能内部 | 先做热盖等三项设置（见下）。把阶段编译成设备的步骤表（A、C 区同温；块的最后一步带循环次数和跳回的步号，步号从 1 起算），发 `RunProgram{Steps: JSON 字符串}`，核对 10 秒内 `PcrState=Running`，给板记一条“程序已启动”的经历（含阶段内容和预计时长）。立即返回 |
| 给人看的文本 | `98℃ 1 分钟 →（98℃ 10 秒 → 60℃ 5 秒 → 72℃ 5 秒）× 23 → 72℃ 1 分钟` |
| 循环次数的含义 | 按“一共跑 n 遍”编译。依据：PDF 的 0x03C0 写着“循环次数范围 1～99，为 1 时忽略跳转字段，当前步骤运行结束直接运行下一步”，即 1 表示只跑一遍。步骤 8 用一个 2 次循环的短程序复核 |

**热盖加热（用户 2026-11-18 同意放开）**

实测这台 PCR 现在热盖加热是关的（`HeaterLidEnabled=false`，热盖 27℃，设备里存的热盖目标是 105℃），`PlateCapacity=0`，模式是 `Block`。厂商协议的操作范例（《自动化热封PCR仪属性定义》附录 A）在运行程序前先设置三样：热盖温度（0x011A）、Tube 模式（0x03C4）、液体微升数（0x03C7）。冷盖下跑 90℃ 和 98℃，孔里的液体会蒸发到盖上。

允许清单新增三个底层动作，各带规则（写在 `pcr/rules.py`）：

| 底层动作 | 规则 |
|---|---|
| `SetHeater` | 只允许 `Zone=Lid`（A、B、C 区只能由程序控制）。开启时门必须关着、热盖必须压下；`TargetCelsius` 30～110。上限 110 是暂定值，与厂商确认 |
| `SetPlateCapacity` | `Microliters` 1～255（设备范围 0～255） |
| `SetTubeMode` | 只允许 `Mode=Block`（设备当前的模式）。`Tube` 模式温度会过冲，不用 |

`pcr_start_program` 增加两个参数：

| 参数 | 含义 |
|---|---|
| `volume_ul` | 孔内液体体积，1～255，必填 |
| `lid_c` | 热盖温度，30～110，缺省 105。可以填空表示不加热热盖，这时各阶段温度不得超过 45℃（暂定值，用于 37℃ 这类低温程序） |

技能内部的顺序：`SetTubeMode{Block}` → `SetPlateCapacity` → `SetHeater{Lid, 开, lid_c}`（核对 `HeaterLidEnabled=true`）→ `RunProgram`。`pcr_confirm_finished` 和 `pcr_stop` 关掉热盖加热（`SetHeater{Lid, 关}`）并核对。

**热盖打开之后程序没启动起来**（实测复现过：`RunProgram` 失败后热盖一直加热，板在里面）：

| `RunProgram` 的结果 | 技能怎么做 |
|---|---|
| 被互锁拦下，或设备报失败 | 先关掉热盖加热并核对，再把原来的异常抛出 |
| 没等到结果，或核对不上（已冻结） | 不动。程序可能已经在跑，由到现场的人决定；人点“全部停止”会关热盖 |

这类“出错后把设备收回安全状态”的写法（`try … finally`）是允许的，它不吞异常（第 12 节第 3 条）。

2026-11-18 实测（详见 02）：

| 问题 | 结果 |
|---|---|
| `RunProgram` 能否用、多快返回 | 能。0.22～0.25 秒返回，立即 `Running`，网关不被占用。“10 秒内进入 Running”的核对成立 |
| 温度编码 | 设备按“温度×100”执行（不是文档写的“(温度+100)×100”）。我们经驱动下发，不受影响 |
| 循环次数 | 一共跑 n 遍，和本节的编译方式一致 |
| 热盖多久到温 | 28→104℃ 约 100 秒。`SetHeater` 后 `HeaterLidEnabled=true` 的核对成立 |
| `RunProgram` 会不会动热盖 | **会**。程序运行时热盖由 PCR 自己控制：开始时关约 10 秒再开；进入 4℃ 那一步时关掉，程序结束也不再开 |
| 程序会不会等热盖到温 | 没测到（这次热盖已经是热的）。程序开始前有约 20 秒“第 0 步”准备阶段 |
| 程序结束后热盖 | 是关着的。`pcr_confirm_finished` 里再关一次无害 |
| 板容量、模式 | 设置都能用；遥测里的 `PlateCapacity` 一直是 0，不准，不能拿来核对 |
| 暂停、继续、停止 | 0.37、0.36、0.53 秒返回，2 秒内生效，都不占住网关 |

还没测：冷热盖时下发高温程序，设备会不会自己开热盖、会不会等它到温。

“未开放技能”清单在各后端里：虚拟后端为空；真实后端（`mqtt/backend.py`）列出还没在现场陪同首跑通过的技能，通过一个删一个。

**未开放的技能在提交和批准时就拦下**（实测复现过：含未开放技能的方案通过了预演和批准，门关上之后第 2 步才失败）：

| 环节 | 做法 |
|---|---|
| 服务启动 | 把后端的 `closed_skills` 写进数据库的 `meta` 表（第 5.13 节） |
| `protocol/validate.py` | 从数据库读这份清单，方案里用到其中任何一个就报问题：“第 n 步：技能 X 在这座实验岛上还没有开放”。预演、提交、批准前的重新预演都经过它 |
| Agent 的 `list_skills` | 每个技能带一个“是否开放”的标记，来源同上 |
| `registry.call` 里的检查 | 保留，作为最后一道 |
| `stop_all` | 仍然不受清单限制（第 5.14 节） |

### 5.9 方案（protocol/）

**方案是什么**：Agent 交上来、人要批准、服务要执行的那份东西。一串步骤，每步是一次技能调用或一次等待。

```json
{
  "name": "37℃ 保持 30 秒",
  "labware": {"LW-001": "pcr"},
  "steps": [
    {"skill": "pcr_close", "args": {}},
    {"skill": "pcr_start_program", "args": {"stages": [{"temperature_c": 37, "hold_seconds": 30}], "volume_ul": 50, "lid_c": null}},
    {"wait_until": {"device": "pcr", "state": {"PcrState": "Idle"}, "max_seconds": 600}},
    {"skill": "pcr_confirm_finished", "args": {}},
    {"skill": "pcr_open", "args": {}}
  ]
}
```

这份方案要求板已经在 PCR 里：没有板时关门后热盖不会压下，互锁不允许开始加热。

| 文件 | 内容 |
|---|---|
| `model.py` | 用 pydantic 定义格式。三种步骤：技能调用；`wait: {seconds}`；`wait_until: {device, state, max_seconds}`。`device` 用短名。线性，没有分支和循环；要根据结果做选择，由 Agent 在两份方案之间决定。`fingerprint(方案)`：JSON 规范化后的哈希 |
| `validate.py` | 技能存在、参数合法、`labware` 与账本一致、没有用到这座岛未开放的技能（第 5.8 节）。返回问题列表 |
| `run.py` | `run_step(lab, step) -> 结果`。技能调用走 `registry.call`；`wait` 走 `backend.sleep`；`wait_until` 每秒读一次状态 |
| `rehearse.py` | `rehearse(conn, 方案)`：从数据库快照生成场景，建一个虚拟后端和一个内存数据库，在上面逐步执行整份方案。返回每步结果、每步耗时、总时长、第一处过不去的步骤及原因和当时的状态、事故列表。只读数据库，不需要后端，所以 Agent 进程和界面进程都能调用 |
| `render.py` | `render(方案, 预演结果)`：程序生成的中文文本。每步一句、预计耗时、每块板的去向、预演结论，开头列出“执行前现场应该是这样”（每块板在哪）。人看到的和将要执行的是同一份数据 |

`wait_until` 的结束条件：

| 情况 | 结果 |
|---|---|
| 状态对上了 | 这一步完成 |
| 超过 `max_seconds` | 这一步失败 |
| 等待期间该设备带报错（`_error`、`WorkingStatus=2`，或它的 `rules.fault` 给出原因） | 这一步失败，原因写明 |
| 看不到这台设备的新状态（超过 10 秒没有完整的一帧） | 继续等，不判失败。抓包里出现过 6 秒的间隔，网络抖一下不应该让一个两小时的程序作废 |
| 连续 60 秒看不到它的新状态 | **冻结**，原因写明“等待期间失去 XX 的状态”，写事件。这一步保持 `waiting`，不记失败：设备上的程序多半还在跑。人解除冻结后接着等；截止时间不变，已经过了截止时间就按超时失败 |

`wait_until` 只知道“状态到了”，不知道程序是不是正常跑完的（中途被停也会回到 Idle）。所以启动程序的技能后面固定跟三步：等待、确认完成（`pcr_confirm_finished`）、收尾。

### 5.10 虚拟后端（sim/）

| 文件 | 内容 |
|---|---|
| `backend.py` | `SimBackend(scenario)`。`call`：先查故障注入；按厂商编码从 `ISLAND` 找到设备和它的 sim（读还是动查该设备的 `ACTIONS`），把动作方法作为 SimPy 进程跑到结束；失败时把该设备的 `WorkingStatus` 置 2，成功后置 0；未知动作报失败。`state`：汇总各 sim 的属性。`now`、`sleep`：虚拟时钟。`closed_skills` 为空 |
| `world.py` | 真相账：每块板真实在哪、真实经历了什么。事故列表 `accidents`。按短名查到某台设备的 sim。Agent 看不到这里的东西 |
| `scenario.py` | 场景格式（pydantic）：起始时间、初始器皿位置、设备属性覆盖值、故障注入列表。`from_snapshot(快照)`：从数据库快照生成场景；PCR 正在运行时按剩余时间续上 |
| `faults.py` | 故障注入：“第 n 次调用某设备某动作时，报失败 / 无应答” |

| 规定 | 内容 |
|---|---|
| 确定性 | 不使用随机数。同一场景同一串调用，操作记录逐条相同 |
| 虚拟岛配文件数据库 | 服务启动时用 `from_snapshot` 从库里的设备状态和器皿位置续上，时钟从库里最后一个时间继续。所以虚拟岛的服务可以重启，时间不会倒退 |
| 程序时长 | PCR 程序的虚拟时长要包含升降温时间，保持时间从到温后才开始计。2026-11-18 实测（Block 模式，热盖 105℃）：升温平均约 2℃/秒；降温约 0.029 × 当前温度 ℃/秒（90℃ 时约 2.6，20℃ 时约 0.55）；开始前约 20 秒准备阶段。按这些值模拟（第 16.6 节第 33 项） |

现在不模拟机械臂的几何运动、液体和测量结果。

### 5.12 真实后端（mqtt/）

实现 01 第 3 节的全部规则，用 paho-mqtt。

| 文件 | 内容 |
|---|---|
| `codec.py` | 纯函数。组装指令报文。解析上行报文分两层：先做网关层（见下表），再把应答交给该设备 `spec.py` 的 `result_ok`。用 `captures/` 里的录制做测试，不需要设备 |
| `client.py` | 连接（地址和账号密码来自 `.env`）、断线自动重连、订阅、发布。把每条原始报文追加到这座岛文件夹下 `raw/` 里按日期分的文件 |
| `telemetry.py` | 维护状态表、设备报错、网关心跳、别人发来的指令（见下表） |
| `commands.py` | 一条指令只发布一次；按操作编号等最终应答（编号由 `Lab` 传入，就是报文的 `requestId`，这里不另外编号）；超时抛 `NoResult`；设备报失败抛 `DeviceFailed` |
| `backend.py` | `MqttBackend`：实现后端接口。`now` 是系统时间，`sleep` 是 `time.sleep`。`closed_skills` 初始为：`pcr_start_program`、`pcr_confirm_finished`、`pcr_stop`、`shake_start`、`shake_stop`、`transfer`、`rotate_turntable` |

**网关层的解析规则：**

| 规则 | 原因（都有抓包证据） |
|---|---|
| **所有上行报文只认 `GatewayCode=GW_001`**，其余丢弃 | 设备主题里没有网关编码。GW_002 上也注册了一台叫 `TYPE_ROBOT_ARM001` 的机械臂，往同一个遥测主题发数据。不过滤的话，它会盖掉 GW_001 机械臂的状态 |
| 忽略“已收到”回执（`rpc-response`），只认 `rpc-result` | 三个网关都会回“已收到” |
| 外层 `Body.Data.success` 不作为通用依据，交给各设备的 `result_ok` | 对 PCR 它恒为 true（驱动报“找不到设备”时也是）；对机械臂它是有意义的 |
| `deviceData` 是字符串（如 `"ERROR: device not found"`）→ 失败 | 实测出现过 |
| 没有 `Data` 字段 → 看 `Body.code`，`"0"` 成功 | 网关异常分支 |
| 认不出的报文：原样存档、计数，不影响接收线程 | 见第 12 节第 2 条 |

**`telemetry.py` 维护的东西：**

| 内容 | 做法 |
|---|---|
| 状态表 | 按属性合并遥测。`_age_s` 只在收到含 `STATE_PROPS` 的帧时刷新；只含 `error` 的帧不刷新 |
| 设备报错 | 帧里有非空的 `error` → 该设备 `_error` 记下文本；收到不含 `error` 的完整帧 → 清空 |
| 网关心跳 | 订阅 `lab/v1/gateway/GW_001/telemetry`，超过 10 秒没收到 → `_gateway.online=false` |
| 别人发来的指令 | 订阅 GW_001 各设备的请求主题和网关级的 `motion/request`，看到编号不是 `WL-` 开头的请求且还没见到它的结果 → `_gateway.busy_by_others=true`。一条外来请求 300 秒没见到结果就不再算数并记一条日志（格式错误的请求网关根本不回，不设期限会永远占着）。300 秒是暂定值：抓包里厂商的一次搬运从发出到失败用了 128 秒，原先定的 120 秒会提前放行 |

`tools/gen_device_manual.py` 现在也没有按 `GatewayCode` 过滤，已经把 GW_002 的报错写进了 02（“Dobot 连接失败……来源不明”那一句）。步骤 1 一并改正。

**机械臂搬运开放前要解决的**（第 13.1 节）：发给 `TYPE_ROBOT_ARM001` 设备主题的指令，GW_002 上的同名设备也会收到。要么让现场去掉 GW_002 上重复的设备编码，要么搬运指令改走网关级的主题（《MQTT接口对接文档》第 13.1 节）。

### 5.13 数据库（store/）

每座实验岛一个 SQLite 文件，三个进程共用。预演和测试用内存数据库，代码相同。时间列都存 `backend.now()`。

**虚拟岛和真机分开：**

| 规定 | 内容 |
|---|---|
| 路径 | 虚拟岛：`runs/virtual/wetlab.sqlite`；真机：`runs/real/wetlab.sqlite`。同一个文件夹下放这座岛的全部东西：`agents.sqlite`、`raw/`、各任务的文件夹。路径规则只写在 `store/db.py` 一处，命令行和网页按 `--mode`（或环境变量 `WETLAB_MODE`，缺省 `virtual`）取 |
| 库记着自己是谁 | `meta` 表存 `island_mode`（real / virtual）和 `db_id`（建库时生成的随机编号） |
| 服务启动时核对 | 库是新的 → 写入本次的模式。库里已有模式且和本次 `--mode` 不同 → 报错退出，一条指令都不发 |
| Agent 的存档跟着库走 | `agents.sqlite` 里记下它对应的 `db_id`。Agent 进程启动时两边对不上 → 报错退出（主库被删掉重建后，旧对话不能接到新任务上） |
| 任务的 `mode` | 由服务按库的模式填，不由发命令的人指定 |

原因：两种岛共用一个文件时，虚拟岛上登记的器皿会被真机当真；虚拟岛上批准后没跑完的方案（状态 `running`），换成真机模式启动后会在真设备上接着执行。

| 规定 | 内容 |
|---|---|
| 打开时的设置 | `journal_mode=WAL`、`busy_timeout=5000`、`foreign_keys=ON`。每个进程、每个线程用自己的连接 |
| 事务 | `store/` 里的函数只执行语句，不提交。由调用方把“一件事”包成一个事务：服务处理一条命令是一个事务，`Lab.do` 记录一条操作是一个事务 |
| 表结构变更 | `migrations/` 下按编号的 SQL 文件；库里用 `PRAGMA user_version` 记已执行到哪个编号；`db.py` 打开时执行还没执行的。以后加表（如孔内液体、枪头）就是加一个新编号的文件 |

| 表 | 列 | 说明 |
|---|---|---|
| `missions` | `id`, `title`, `input_text`, `mode`（real/virtual）, `status`, `created_at`, `conclusion` | 一项任务 |
| `experiments` | `id`, `mission_id`, `n`, `task_json`, `status`, `notes` | 一个实验；`task_json` 是任务单；`notes` 是操作员写的说明 |
| `protocols` | `id`, `experiment_id`, `version`, `content_json`, `fingerprint`, `rehearsal_json`, `text_md`, `status`, `submitted_at`, `decided_by`, `decided_at`, `reject_comment` | 一份方案。修订方案是同一实验下 `version` 加 1 的新行 |
| `steps` | `protocol_id`, `n`, `kind`, `content_json`, `status`, `started_at`, `finished_at`, `result_json`, `wait_deadline` | 方案的每一步 |
| `operations` | `id`（WL-…）, `seq`, `protocol_id`（可空）, `step_n`（可空）, `device`, `action`, `params_json`, `status`, `result_json`, `error_code`, `started_at`, `elapsed_s` | 每条底层指令。不属于任何方案的操作（服务启动时的只读查询、以后评测模式下的直接调用）`protocol_id` 为空 |
| `labware` | `id`, `type`, `position`（可空：已拿走） | 每块板现在在哪 |
| `labware_events` | `id`, `labware_id`, `at`, `what`, `detail_json`, `operation_id`, `by` | 每块板的经历；`by` 是设备动作还是人 |
| `device_state` | `device`, `props_json`, `error`, `updated_at` | 各设备最新状态，另有一行是网关。服务每轮写一次。网页和 Agent 读它 |
| `freeze` | `frozen`, `reason`, `operation_id`, `at` | 只有一行 |
| `commands` | `id`, `key`（唯一）, `at`, `who`, `kind`, `target_id`, `payload_json`, `handled_at`, `outcome` | 界面和 Agent 发来的命令和处理结果。`key` 相同的命令只收一次 |
| `events` | `id`（递增）, `at`, `kind`, `ref_id`, `payload_json` | 发生的事 |
| `cursors` | `name`, `last_event_id` | 每个读事件的人读到哪了（`agents`、`notify`） |
| `meta` | `key`, `value` | 这个库自己的信息：`island_mode`、`db_id`、`closed_skills`（JSON 列表，服务每次启动时按后端的清单重写）。用一个新编号的变更文件加这张表 |

不进数据库的：原始 MQTT 报文（`raw/`）、Agent 的对话存档（`agents.sqlite`）、报告文件。它们都在这座岛自己的文件夹下。

### 5.14 服务（service/）

一个常驻进程，开机自启，崩溃后自动重启。单线程，同一时刻只做一件事。它不调用模型，不等任何慢的东西。

**状态转换（都在 `advance.py`）：**

| 对象 | 状态 |
|---|---|
| 方案 | `submitted` → `approved` 或 `rejected`；`approved` → `running` ⇄ `paused` → `done` / `failed` / `stopped` / `aborted` |
| 技能步骤 | `pending` → `sent`（调用技能前先落盘）→ `done` / `failed` / `unknown` |
| 等待步骤 | `pending` → `waiting`（落盘截止时间）→ `done` / `failed` |

冻结是整座实验岛的状态，在 `freeze` 表，不混在方案状态里。

**每秒一轮（`loop.py`），顺序固定：**

```
1. 读 commands 表里未处理的命令，逐条处理（每条一个事务）
2. 把最新设备状态和网关状态写进 device_state
3. 网关从在线变成不在线 → 冻结，写事件
4. 没冻结、有 running 的方案：
     当前步骤是 waiting → 按第 5.9 节的结束条件判断
     当前步骤是 pending → 技能步骤：记 sent，调用 run_step，记结果
                          等待步骤：记 waiting 和截止时间
     某步 failed → 方案记 failed，写事件
     全部 done → 方案记 done，写事件
5. 通知：读 notify 的读取位置之后的事件，发通知，前移读取位置
6. backend.sleep(1)
```

一个技能调用期间（最长约一分钟）服务不读命令。这和厂商网关逐条处理指令一致：这段时间停止指令本来也到不了设备。

循环里出现意料之外的异常：冻结，写事件，继续循环。

**处理某一条命令时出错不属于这一类。** 命令是外面进来的东西（Agent 写的、人在界面上填的）。做法：

| 情况 | 做法 |
|---|---|
| 命令的内容 | 每种命令的 `payload` 用一个 pydantic 模型校验（第 12 节第 2 条） |
| 校验不过，或处理中抛出异常 | 回滚这条命令做的改动，把它记为已处理、结果为失败并写明原因，继续处理下一条。**不冻结** |
| 失败的命令是 Agent 发的 | 再写一条事件 `command_failed`（带命令种类、原因、任务或实验编号），唤醒发命令的那个 Agent |
| 失败的命令是人发的 | 界面显示处理结果 |

实测复现过原来的做法的后果：一条处理时报错的命令不会被记为已处理，每秒被重试一次、每次都冻结，排在它后面的命令（包括“解除冻结”）永远轮不到，只能手工改数据库。

**命令（`commands.py`，每种一个函数）：**

| 命令 | 谁发 | 处理 |
|---|---|---|
| `new_mission` | 界面 | 建任务，写事件 `mission_created` |
| `place_labware` / `remove_labware` / `correct_labware` | 界面 | 调器皿账本的对应函数 |
| `create_experiment` | 协调者 | 建实验和任务单，写事件 `experiment_created` |
| `submit_protocol` | 操作员、命令行 | 校验（含未开放技能）并预演。通过则存方案、预演结果和给人看的文本，写事件 `protocol_submitted`；不通过则记 `rejected`，原因是预演结果，写事件 `protocol_rejected`。同一个实验最多 5 版方案：第 6 次提交直接把实验记为 `failed`（说明“方案修改次数超过上限”），写事件 `experiment_finished` |
| `approve` | 界面 | 必须带批准人的名字和方案指纹。指纹与库里一致、且重新预演通过（现场可能已经变了）才进入 `running`；否则记 `rejected`、写原因、写事件 `protocol_rejected` |
| `reject` | 界面 | 记退回意见，写事件 `protocol_rejected` |
| `pause` / `resume` | 界面 | 方案进入 `paused` / 回到 `running`。设备上已在跑的程序不受影响。`resume` 只对 `paused` 的方案有效，对 `stopped` 的方案会被拒绝 |
| `stop_all` | 界面 | 对正在运行的设备调停止技能（`pcr_stop`、`shake_stop`，它们会关热盖、记下实际运行时长；停止不受未开放清单限制，**冻结时也照样发**，见第 5.5 节）。方案记 `stopped`，当前步骤记 `failed`，原因“被人工停止”，写事件 `protocol_stopped`。**任何一台设备的停止技能没有成功：命令结果记为失败并列出是哪台，写事件 `stop_failed`（通知人到现场），界面用醒目的方式显示“XX 没有停下来”。** 方案仍然记 `stopped`（服务不会再发后面的步骤）。**停止之后不能“继续”**：设备上的程序已经被打断，剩下的要做什么由操作员出修订方案、人重新批准，或者人直接终止 |
| `unfreeze` | 界面 | 必须带人的结论：`step_done` / `step_failed` / `abort`。那一步如果是搬运，还必须带那块板现在的实际位置，先更正账本。然后按结论把那一步记为 `done` 或 `failed`（不重新执行）；结论是 `abort` 时按下面 `abort` 的方式处理；解除冻结 |
| `abort` | 界面 | 人终止这个实验。方案记 `aborted`，实验记 `stopped`（说明写“人工终止”），写事件 `experiment_finished`，协调者会被唤醒 |
| `reply` | Agent 进程 | Agent 给人的一段话，写事件 `reply`，显示在对话页 |
| `finish_experiment` | 操作员 | 记实验状态和说明，写事件 `experiment_finished` |
| `ask` | 协调者 | 写事件 `question_asked`（人会收到通知） |
| `message` | 界面 | 人给 Agent 的留言或对提问的回答，写事件 `message` |
| `finish_mission` | 协调者 | 记结论，生成报告（`service/report.py`，第 6.5 节），写事件 `mission_finished` |
| `agent_error` | Agent 进程 | Agent 进程自己出了问题（如模型接口连续报错），写事件 `agent_error`，通知人 |

`wetlab submit 方案文件` 发一条 `new_mission` 和一条 `submit_protocol`，和 Agent 提交的方案走同一条路。

**事件由谁读：**

| 事件 | 通知人 | 唤醒哪个 Agent |
|---|---|---|
| `mission_created` | | 协调者 |
| `experiment_created` | | 操作员 |
| `protocol_submitted` | 是：请审阅 | |
| `protocol_rejected` | | 操作员 |
| `protocol_done`、`protocol_failed`、`protocol_stopped` | 是 | 操作员 |
| `reply` | 是 | |
| `experiment_finished` | | 协调者 |
| `question_asked` | 是：请回答 | |
| `message` | | 协调者 |
| `frozen`、`gateway_offline`、`stop_failed` | 是：请到现场 | |
| `command_failed` | | 发那条命令的 Agent（按命令的 `who` 和编号找到线程） |
| `agent_error` | 是 | |
| `mission_finished` | 是 | |

服务只负责写事件和发通知。Agent 进程自己按读取位置读事件（第 6 节）。

**启动和重启对账（`reconcile.py`）：**

| 做什么 | 说明 |
|---|---|
| 核对库的模式 | 第 5.13 节。对不上就退出，不连后端 |
| 写下未开放技能清单 | 把后端的 `closed_skills` 写进 `meta` 表（第 5.8 节） |
| 先等状态到齐 | 连上后端后，最多等 10 秒，直到收到网关心跳和每台设备的一帧完整状态（或它的报错）。这之前不做任何判断，不把“还没收到心跳”当成掉线 |
| 对每台有只读功能的设备发一次只读查询 | 确认指令这条路是通的。它不是用来拿状态的（状态只来自遥测）。转向台没有只读功能，跳过 |
| 步骤是 `pending`、`waiting` | 照常继续 |
| 上一步是“启动后立即返回”的技能，设备程序在跑 | 不需要特殊处理，后面的 `wait_until` 读遥测判断 |
| 步骤是 `sent`（技能调用发出去了，没有记到结果） | 冻结。人到现场确认后用 `unfreeze` 给出结论 |

**某一步失败之后（清掉设备的“上一条指令失败”标记）：** 设备失败一次后 `WorkingStatus` 停在 2，它的所有动作都会被互锁拦住，直到它下一条指令成功（第 5.6 节）。机械臂和振荡没有只读技能，方案里清不掉。所以：一个技能步骤以 `failed` 结束后，服务对状态里 `WorkingStatus=2` 的每台设备发一次只读查询（和启动时用的是同一个函数、同一个动作）。查询本身失败就不再管它，原因留在操作记录里；没等到结果按 `Lab.do` 的规定冻结。转向台没有只读功能，它失败后要重启服务或由现场处理。已在抓包里看到一次成功的只读查询能清掉 PCR 和振荡的标记；机械臂的待步骤 8 核实（第 13.2 节）。

**通知（`notify.py`）：** 渠道（飞书、企业微信或邮件）由用户确定后再写，不先写临时版本。发送带超时，失败只记录，不影响循环。

**运行在哪：** 一台不关机、接实验室网线、能访问模型接口的电脑。演示阶段用用户的 Mac（设置不休眠），之后换常驻小主机。

### 5.15 三条运行规定

**一、占网关的技能要短，长时间只出现在等待里**

| 规定 | 原因 |
|---|---|
| 一个技能占住网关不超过约 1 分钟（机械臂搬运本身就要这么久，这是下限） | 占住期间暂停和停止都无效；技能越短，执行到一半进程死掉的情况越少 |
| 长时间运行拆成：启动、等待、确认完成、收尾。例：`pcr_start_program` → `wait_until` → `pcr_confirm_finished` → `pcr_open` | 等待存在数据库里，可以跨重启 |
| 长时间运行一律用“启动后立即返回”的底层指令（`RunProgram`、`StartShake`），不用占住网关的（`RunFile`、超过 60 秒的 `StartShakeTimed`） | 同第一条 |

**二、批准**

| 规定 | 内容 |
|---|---|
| 真机只执行已批准的方案 | 批准记录：谁、什么时候、方案指纹 |
| 批准前人要核对现场 | 审阅页开头列出“执行前现场应该是这样”，人勾选确认后才能点执行 |
| Agent 不能让真实设备动，也不向设备发任何指令 | Agent 手里只有：看状态（读数据库）、预演、提交方案 |
| 执行中要改做法 | 某步不成功后，操作员提交修订方案（只含剩余步骤），重新预演、重新批准 |
| 退回 | 人可以退回方案并写意见，意见交给操作员 |
| 以后：拍照核对 | 给 Agent 加一个看现场的工具（如 `capture_image`），搬运后由它判断板到没到位。发现问题时：岛冻结，Agent 提交修订方案，人批准后执行（用户 2026-11-18 决定）。现在不做，也不加人工确认；抓取可靠性由现场在底层保证 |
| 以后 | 可加“任务授权范围内自动批准”，用于过夜的多轮实验，以及一次实验内部必须几分钟内衔接的步骤（例如测完浓度立刻按每孔的读数补液；等人批准的时间里样品会蒸发或降解）。现在不做 |

**三、暂停和停止的限制**

GW_001 逐条处理指令（01 第 3.5 节，实测）。机械臂搬运（约 40～60 秒）、开关门（约 5 秒）、热盖动作（约 8 秒）、60 秒以内的定时振荡进行期间，停止指令要等该动作结束才能到达设备。运动过程中要立即停下，只能按物理急停。界面上要把这一点写明。

待实测（步骤 8）：`RunProgram` 启动后网关是否空闲、`StopRun` 多久生效。
待问厂商：机械臂运动中有没有能插队的停止通道。

**Index 的规则**：一次搬运只有一个 `Material.Index`。两端有一端是料架，用料架那一端的；两端都不是料架，用 `1-1`。依据：厂商调度每次都填料架那一格的编号，去程回程相同；实测“底层点位 + `1-3`”的抓取高度与示教点位一致（Z 365～367 对 367.0），Index 没有改变抓取位置。厂商也说不清它的作用，所以只要和我们的规则一致即可（用户 2026-11-18 决定）。

**网关怎么执行一次搬运**（2026-11-18 现场录制，`captures/20261118_arm_141121.jsonl`）：网关的运动插件按两个点位的姿态自己规划。料架（0）到 PCR（90）插入转向台换夹，共 14 步：转向台转到 0° → 反向夹爪 → 前往料架 → 夹取 → 合并移动到转向台 → 放开 → 抬升 → 转向台转到 90° → 夹爪调整（窄夹换宽夹）→ 下降 → 夹取 → 合并移动到 PCR → 放开 → 返回，约 58～65 秒；反向 16 步。姿态相同时（料架到洗板机）6 步、约 41 秒。每步在 `motion/progress` 上报。**网关报“成功”不代表板真的被搬过去**：2026-11-18 现场两次没夹到板，网关都报成功。

**怎么用**：

| 环节 | 做法 |
|---|---|
| 读入 | `wetlab/lab/devices/positions.py` 在启动时读 `positions.json` 和它指向的 vendor 文件，生成 `POSITIONS`、`POSITION_DEVICE` 等表（取代各设备 `spec.py` 里的 `POSITIONS`）。用环境变量 `WETLAB_ISLAND`（缺省 `GW_001`）选文件夹。虚拟岛用同一份 |

| 换新点位 | 现场重新示教后，从网关导出 `Position.json`，运行 `wetlab points import <文件>`：校验格式（01 第 14.2 节的字段）、和上一份比较（新增、删除、每个点位最终位置的坐标变化），打印给人看；人确认后存成 `vendor/Position_<日期>.json` 并更新 `positions.json` 的 `source`。**这个工具只改仓库里的文件，不向网关发任何东西**（`SyncLocation` 永远不发） |

`docs/Position_20261118.json` 是 `island/GW_001/vendor/Position_20261118.json` 的副本（SHA-256 相同，`a668142f…`），删掉，只留 `island/` 下的。

## 6. Agent 系统（agents/）

### 6.1 两个角色，各自独立的会话

| | 协调者 Coordinator | 操作员 Operator |
|---|---|---|
| 对应白皮书 | 研究规划 Agent | 设备 Agent |
| 负责 | 一项研究任务：理解目标或 SOP，拆成实验，决定先后，解读结果，和研究人员沟通，写结论 | 一个实验：把任务单写成方案，预演，改到能过，提交；执行出偏差时提交修订方案；最后写说明 |
| 会话 | 每项任务一个，线程编号是任务编号 | 每个实验一个，线程编号是实验编号，从空白开始 |
| 工具 | `get_lab_state`、`list_skills`、`read_sop`、待办清单、`create_experiment`、`ask_researcher`、`finish_mission` | `get_lab_state`、`list_skills`、`read_sop`、`rehearse`、`submit_protocol`、`finish_experiment` |
| 模型 | 可单独配置 | 可单独配置 |

**为什么不用“操作员作为协调者的一个工具”**：提交方案之后要等人批准、等设备执行，可能是几天。把操作员当成一次工具调用，就要么在实验还没执行时就返回，要么在调用中间挂起几天；LangGraph 在恢复时会把被挂起的节点从头重跑，操作员的推理和提交会被重复执行。所以两个角色都是“一轮一轮”地工作：

- 每一轮由一个事件开始，以一次写命令的工具调用结束。
- 写命令的工具（`create_experiment`、`ask_researcher`、`finish_mission`、`submit_protocol`、`finish_experiment`）一调完，这一轮立刻结束，模型不再被调用。用 `create_agent` 自带的做法：工具设 `return_direct=True`。
- 一轮只能发出一条这样的命令，由数据库保证：这一轮所有“结束类”命令共用同一个 `key`（见 6.4 的“命令不重复”），`commands` 表的 `key` 是唯一的，所以第二条写不进去。工具发现没写进去时：库里已有的那条和自己要发的种类、内容都相同（进程重启后重放同一次调用）→ 返回成功；否则 → 返回一条明确的错误“这一轮已经发出过 XX 命令”，不能告诉模型成功。
- 为什么两样都要：`return_direct=True` 只在“这条消息里调的工具全都是 `return_direct`”时才结束这一轮，而且模型在一条消息里同时调两个工具时，LangGraph 会把它们并行全部执行完（已对照安装版本的源码）。所以它只是让正常情况少调一次模型，保证“只有一条”的是上面的 `key`。并行执行意味着不能用内存里的标记来判断先后，只能靠数据库。
- 两轮之间没有任何进程在等，也不用 `interrupt()`。
- 交接的内容在数据库里：任务单、方案、结果。

以后加角色（分析、文献、审查）用同样的方式，或者——如果它当场就能返回——作为协调者的一个普通工具。保留单 Agent 配置（把要求直接交给操作员）作为可选项，以后用评测数据比较。

### 6.2 文件

| 文件 | 内容 |
|---|---|
| `models.py` | 用 `langchain.chat_models.init_chat_model` 按 `.env` 建模型对象。两个角色可各配一个，不配则共用 |
| `tools.py` | 两个角色的工具。`get_lab_state` 调 `lab.snapshot`；`list_skills` 调 `registry.catalog` 并标出哪些未开放（第 5.8 节）；`read_sop` 按名字读 `sops/` 下的文件；`rehearse` 调 `protocol.rehearse`；其余的往 `commands` 表写一条命令。状态这类只有几种取值的参数用枚举，不用自由文本。工具每轮需要的任务编号、实验编号通过 `create_agent` 的 `context_schema` 传入，不为每一轮重新建工具和 Agent |
| `operator.py` | 用 `create_agent` 建操作员：工具、提示词、中间件（工具调用次数上限、对话压缩） |
| `coordinator.py` | 用 `create_agent` 建协调者：工具、提示词、中间件（待办清单、对话压缩、次数上限） |
| `handoff.py` | 任务单和实验结果的格式（pydantic）；把一个事件变成给 Agent 的一条消息；从数据库生成实验结果的事实部分 |
| `worker.py` | Agent 进程的主循环（见 6.4） |
| `prompts/coordinator.md`、`prompts/operator.md` | 提示词，只写职责和规矩。下面三样不手写：① 实验岛说明和技能目录（含参数范围）由程序从 `registry.catalog()` 填入——这一条已经是这样做的；② Agent 自己那几个工具的名字、参数、说明，模型本来就会随工具定义收到，提示词里不再抄一遍签名，规矩里提到工具时只写名字；③ 方案示例从 `sops/` 下一份有预演测试的文件读入，不在提示词里另写一份 JSON |

`agents/` 里没有生成报告的代码：报告由服务生成（第 6.5 节）。

模型配置（步骤 9 时更新 `.env.example`）：

```
LLM_MODEL=openai:某模型名          # 格式是 提供方:模型名，如 deepseek:deepseek-reasoner
LLM_BASE_URL=
LLM_API_KEY=
OPERATOR_LLM_MODEL=                # 可选，不填则和上面相同；另有对应的 BASE_URL、API_KEY
```

操作员的三项配置（模型、地址、key）要么全填，要么全不填；只填一部分时启动报错，不逐项回退（否则主 key 会被发到操作员的接口地址）。模型调用设超时（缺省 120 秒，可在 `.env` 里改）。

换成同一种接口的另一个模型只改 `.env`。换到需要专用包的提供方（带思考内容字段的模型，如 DeepSeek），要多装一个依赖包。不依赖并行工具调用和严格模式。

### 6.3 交接内容

协调者交给操作员一张**实验任务单**（`create_experiment` 的参数）：

```json
{"objective": "PCR 仪里的板依次经历三段恒温和一个循环程序",
 "procedure": "37℃ 15 分钟；53℃ 15 分钟；90℃ 10 分钟；……",
 "labware": {"LW-001": "pcr"},
 "constraints": {"max_lab_minutes": 120}}
```

协调者收到的**实验结果**（实验结束时由程序生成，作为一条消息交给协调者）：

```json
{"experiment_id": "E-001",
 "status": "completed | stopped | failed",
 "protocols": [
   {"id": "E-001-v1", "status": "failed",
    "steps": [{"n": 1, "skill": "pcr_close", "status": "succeeded", "elapsed_s": 4.3, "operation_ids": ["WL-…"]}]},
   {"id": "E-001-v2", "status": "done", "steps": ["…"]}],
 "labware": {"LW-001": {"position": "pcr", "history": ["pcr program started …", "pcr program completed"]}},
 "notes": "操作员写的说明：偏差、原因、建议"}
```

除 `notes` 外都由程序从数据库生成。

| 细节 | 规定 |
|---|---|
| `protocols` | 这个实验执行过的每一版方案都列出，各带自己的步骤。不能只给最后一版：前一版里已经做完的和失败的步骤，协调者也要看到。被退回、从未执行的版本只列编号和状态 |
| `labware` | 只列这个实验各版方案的 `labware` 里声明过的器皿；经历只列这个实验期间的 |
| `status` | 实验只有 `completed`、`stopped`、`failed` 三种，任务只有 `completed`、`failed` 两种。工具参数是枚举；服务处理 `finish_experiment`、`finish_mission` 时也按这几种校验 |

### 6.4 一次任务的流程

```
研究人员在网页上写目标、登记器皿位置            → 命令 new_mission → 事件 mission_created
协调者一轮：看状态和技能 → 写计划 → create_experiment      （这一轮结束）
                                                         → 事件 experiment_created
操作员一轮：写方案 → rehearse → 改到通过 → submit_protocol  （这一轮结束）
                                                         → 事件 protocol_submitted → 通知人
研究人员：核对现场，点“执行”；或退回并写意见
   退回 → 事件 protocol_rejected → 操作员一轮：按意见改，再提交
服务：逐步执行，不经过模型；可跨天；可暂停、可停止
   → 事件 protocol_done 或 protocol_failed
操作员一轮：读事实。失败且还能继续 → 提交只含剩余步骤的修订方案
                     否则 → finish_experiment（写说明）       （这一轮结束）
                                                         → 事件 experiment_finished
协调者一轮：读实验结果 → 更新计划 → 下一个 create_experiment，或 finish_mission
程序：报告
```

**例：“把样品 X 做 PCR”**（用户 2026-11-18 给的典型任务）。协调者查账本找到装着 X 的板（如 `LW-003`，在 `rack:1-2`），建实验；操作员写出整份方案、预演、提交，人批准一次，服务逐步执行：

```
pcr_open                                  抬热盖、开门
transfer(LW-003, pcr)                     从 1-2 取板放进 PCR（点位和 Index 由系统按位置取）
pcr_close                                 关门，核对热盖压下（板没放进去会在这里被发现并冻结）
pcr_start_program(stages, volume_ul, lid_c)
wait_until pcr PcrState=Idle
pcr_confirm_finished
pcr_open
transfer(LW-003, rack:1-2)                放回原位（目标位置被占时预演就会拦下）
pcr_close
```

漏了开门之类的错误在预演时就会被拦下，操作员自己改。某一步失败，操作员提交只含剩余步骤的修订方案，人再批准。

**Agent 进程的主循环（`worker.py`）：**

```
循环：
  读 agents 的读取位置之后的下一个事件
  不是要唤醒 Agent 的事件 → 前移读取位置，继续
  在对应的线程上跑一轮（见下面“怎么开始一轮”）
  检查这一轮是怎么结束的（见下表）
  前移读取位置
```

**每种事件，这一轮必须以什么结束：**

| 事件 | 唤醒谁 | 必须以哪种命令结束 |
|---|---|---|
| `mission_created`、`experiment_finished` | 协调者 | `create_experiment`、`ask` 或 `finish_mission` |
| `experiment_created`、`protocol_rejected` | 操作员 | `submit_protocol` 或 `finish_experiment` |
| `protocol_done` | 操作员 | `finish_experiment` |
| `protocol_failed`、`protocol_stopped` | 操作员 | `submit_protocol`（只含剩余步骤的修订方案）或 `finish_experiment` |
| `message`（人的留言） | 协调者 | **不要求。** 实验可能正在等批准或正在执行，协调者只需要回答。这一轮最后的文字由程序作为 `reply` 命令发出；协调者也可以发上面任何一种命令 |
| `message`，且这个任务有一条还没回应的提问 | 协调者 | `create_experiment`、`ask` 或 `finish_mission`。“还没回应的提问”指：这个任务最近一条 `question_asked` 事件之后，协调者还没发过这三种命令。否则协调者回一句话，任务就再也没有事件来推动 |
| `command_failed`（自己上一轮发的命令没被接受） | 发命令的那个 | 和它原本该发的那几种相同（协调者：`create_experiment`、`ask`、`finish_mission`；操作员：`submit_protocol`、`finish_experiment`） |

除 `message` 外，一轮没有以规定的命令结束：提醒一次再跑一轮；仍然没有，程序替它发 `finish_experiment` 或 `finish_mission`，状态为失败，说明写“Agent 没有给出结果”。

**怎么开始一轮（保证进程重启后不重复）：**

线程的状态里除了对话，再加两个字段（用 `create_agent` 的 `state_schema`）：`last_event_id`（最近一次发进来的事件编号）和 `reminded_event_id`（最近一次提醒过的事件编号）。发事件消息时，消息和 `last_event_id` 在同一次写入里落盘。

| 情况 | 怎么判断 | 做法 |
|---|---|---|
| 这个事件还没发进线程 | 线程的 `last_event_id` 小于事件编号 | 把事件变成一条消息发进线程，同时写 `last_event_id` |
| 已经发进去，但那一轮没跑完（上次跑到一半进程死了） | `last_event_id` 等于事件编号，且存档显示还有没执行完的节点 | 不再发消息，从存档接着跑（`invoke(None, config)`） |
| 已经发进去，那一轮也跑完了 | `last_event_id` 等于事件编号，存档里没有待执行的节点 | 检查这一轮的结束方式，前移读取位置 |

**不靠翻对话内容来判断。** 对话压缩会把旧消息整体换成一段摘要，带事件编号的那条消息会消失（实现后的审查复现过：重启后同一个事件被重新发进线程，模型又被调用）。“提醒过没有”同理，看 `reminded_event_id`。

| 细节 | 规定 |
|---|---|
| 存档 | `SqliteSaver`，文件是这座岛文件夹下的 `agents.sqlite`（第 5.13 节）。每步同步落盘：每次 `invoke` 都传 `durability="sync"`（LangGraph 的缺省是异步，进程被杀时最后一步可能没存上）。同一线程编号再次调用就是接着上次的对话 |
| 命令不重复 | Agent 发的命令带固定的 `key`。结束类命令（`create_experiment`、`ask`、`finish_mission`、`submit_protocol`、`finish_experiment`）：`turn:<线程编号>:ev<事件编号>`，**不含命令种类**，所以一轮只可能有一条（6.1）。程序代发的文字回复：`reply:<线程编号>:ev<事件编号>`。`agent_error`：`agent_error:<线程编号>:ev<事件编号>`。方案的版本号由服务分配，Agent 发命令时不知道，所以不用它 |
| 模型接口出错 | 这是外面来的错误，要处理，进程不退出。退避重试（5 秒起，最长每 5 分钟一次）；第一次失败就发一条 `agent_error` 命令通知人；累计 1 小时仍然失败，按“没有给出结果”处理（替它发失败的 `finish_experiment` 或 `finish_mission`，说明写“模型接口出错”），前移读取位置 |
| 一次只跑一个 Agent | 事件按顺序处理 |
| 向人提问 | `ask_researcher` 写一条 `ask` 命令，这一轮结束；人的回答作为 `message` 事件开始下一轮 |
| 计划 | 协调者用官方待办清单中间件，这是计划的唯一来源（存在线程存档里）。每轮结束后程序把清单导出成任务文件夹里的 `plan.md` 给人看 |
| 对话压缩、步数上限 | 官方中间件 |

### 6.5 报告

`report.md` 分两部分并明确标注：

| 部分 | 来源 |
|---|---|
| 事实：每块板经历了什么、每步结果和耗时、偏差、暂停和人工干预、批准记录 | 程序从数据库生成 |
| 说明和结论 | 操作员的 `notes`、协调者的 `conclusion`（都已经在数据库里） |

| 规定 | 内容 |
|---|---|
| 谁生成 | 只有服务，在处理 `finish_mission` 时生成一次，代码在 `service/report.py`。Agent 进程不写报告文件 |
| 只写这个任务的 | 步骤、操作、器皿经历、停止、解除冻结、器皿更正、冻结和掉线，都只取属于这个任务的实验、以及这个任务起止时间之内的。同一个库里别的任务的记录不能出现 |

### 6.6 给 Agent 的现场知识

| 内容 | 是什么 |
|---|---|
| `LAB.md` | 现场的人用大白话写的规矩和经验，每轮自动带给 Agent（相当于编码工具里的 `CLAUDE.md`）。只写经验和规矩（如“高于 45℃ 要开热盖，否则液体会蒸到盖上”），不抄技能的参数范围：范围以技能目录为准，抄一份迟早会不一致 |
| `sops/` | 存好的 SOP 和方案，Agent 用 `read_sop` 按名字查 |

### 7.2 接入粒度

| | 脚本级 | 单步级 |
|---|---|---|
| Agent 做什么 | 从已有脚本里选一个运行 | 自己决定从哪个孔吸多少、排到哪个孔 |
| 需要我们记的账 | 器皿在哪个板位；脚本作为黑箱 | 每孔体积和成分、枪头库存、台面布局 |
| 风险 | 低：流程是人写好验证过的 | 高：VERID 说的三类错误都会出现 |

task.md 要求 Agent 自己选体积、选孔位、换枪头，**需要单步级**。脚本级技能只有在“让 Agent 运行现成脚本”是长期需要时才写；如果只是为了首次上机验证，由现场的人用华大自带软件跑脚本，不为此写代码。摸底后定。

P8 是一台有自己状态的工作站（会弹窗阻塞、查询可能卡住、停止只能停脚本）。现在的后端接口（`call`、`state`）是否够用，摸底后对照第 5.4 节检查，不够就在那时扩展。

### 7.3 单步级检查与孔位/枪头记账（来自 VERID 的经验）

| 层 | 例子 | 怎么拦 |
|---|---|---|
| 物理上做不到 | 8 通道移液头伸进太窄的槽；枪头型号和体积不匹配；目标孔位不存在 | 一张静态表：哪种移液方式能进哪种器皿。在技能参数检查和预演里拦 |
| 物料上不成立 | 从可吸体积不够（扣除孔底死体积后不足）的孔吸液；排液后超过有效工作体积；枪头用完；板位上没有这块板 | 物料账本：每孔体积、成分、来源；枪头库存。在预演和执行前拦 |
| 科学上有偏差 | 贴底排液造成分层；枪头挂壁残留；敞口太久蒸发 | 仿真拦不住。靠完整的过程记录和观测事后发现 |

孔位与枪头记账在 P8 接入时的端到端做法（承接第 5.7 节的 `labware_contents`，表结构经新编号的迁移文件扩展）：

| 环节 | 做法 |
|---|---|
| 初始装料录入（双入口） | 评测/任务侧由 `environment/data/initial_state.json`（第 14.4 节）给出；研究人员日常使用侧由网页“新任务”页和命令行导入孔板物料表（CSV/JSON 或孔位表），登记每块板各孔（如 96 孔板 `A1`～`H12`）的初始物料、体积、浓度/索引及枪头盒余量，经命令写入数据库 |
| 随移液确定性推演与拦截 | 单孔或整列（8 通道，如 `A1`～`H1`）移液技能执行后，自动扣减源孔体积、累加目标孔体积、按体积比例合并成分，并记录样本与索引来源链（如原样本 → 酶处理孔 → DNA 释放孔 → PCR 孔及 R/i7 + F/i5 归属），同步扣减枪头库存并检查换枪头规则防交叉污染。源孔可吸判定必须扣除容器死体积（`当前体积 − 死体积 >= 吸液量`），目标孔排液后不得超过有效工作体积，在预演和执行前统一拦下 |
| 现场核对与人工更正 | ① 方案审阅页的“执行前现场核对清单”在接入 P8 后列出本次涉及的关键孔板、起始样本/试剂孔位与枪头盒供人工勾选确认（防初始摆错孔）；② 当粘稠挂壁、高温蒸发或 P8 液面探测/吸空/堵塞报错导致现场实际液量与账本不一致时，提供与 `correct_labware` 对齐的孔位体积/状态及枪头余量人工更正命令和界面入口，每次更正留痕 |

开工前先查清：开源的 PyLabRobot 的器皿模型（台面、板、孔、枪头盒，以及体积和枪头的记账）能否单独拿来用。能用就用它的，不自己写。它是否有华大 P8 的后端：2026-11-18 检索没有找到，按“没有”做计划。

### 7.4 观测和记录

| 内容 | 做法 |
|---|---|
| 过程变量 | 操作记录已带时间。报告里要能算出每块板的敞口时间、两步之间的间隔 |
| 视频 | 实验岛加一台俯视相机，录制文件存进任务文件夹，文件名带起始时间，可与操作记录对上。它同时能弥补料架没有传感器 |
| 状态可查 | 数据库快照在 P8 接入后包含台面布局、每孔体积、枪头余量 |

### 7.5 测量和闭环

实验岛上现在没有任何测量仪器，Agent 无法根据实验结果决定下一步。这是当前硬件和白皮书目标之间最大的差距（第 15.2 节）。用户的决定：测量是以后要做的事，现在只记录，不排进第 11 节的步骤。可选的补法，按价值从高到低：

| 办法 | 说明 |
|---|---|
| 接入真正的生物读数 | P8 的荧光或定量模块（第 7.1 节第 2 项），或一台读板仪器 |
| 俯视相机加染料 | VERID 用它验证移液和闭环的基础能力。成本最低，适合 P8 的首次陪同实测；但它不是生物测量，不能当作科学成果 |

### 7.6 P8 首次上机的顺序

1. 只读摸底（第 7.1 节）。
2. 用 P8 自带仿真校验一个已有脚本。
3. 空台面、不装枪头，现场陪同跑一个已有脚本。
4. 装水，陪同跑。
5. 之后才开放单步操作和与机械臂的交接。

## 8. 界面（app/）

| 入口 | 给谁 | 文件 |
|---|---|---|
| 命令行 | 开发 | `app/cli.py`，每条命令一个函数：`wetlab serve`（启动服务进程）、`wetlab agents`（启动 Agent 进程）、`submit`、`rehearse`、`approve`、`reject`、`pause`、`stop`、`resume`、`unfreeze`、`abort`、`labware`（登记、拿走、更正）、`status`、`doctor`、`tools export` |
| 网页（Streamlit） | 研究人员 | `app/web/main.py`（入口、全站顶部）加 `app/web/views/`（两个页面，每个一个文件）、`app/web/mission/`（任务的新建和四个视图，每个一个文件）。页面目录不叫 `pages/`，否则 Streamlit 会把它当旧式多页应用自动列出 |

两者都只做两件事：读数据库；往 `commands` 表写命令。任务在服务里运行，关掉浏览器不影响。

命令行的每条命令和网页都按 `--mode`（或环境变量 `WETLAB_MODE`，缺省 `virtual`）找到那座岛的文件夹（第 5.13 节）。网页顶部始终显示当前连的是“虚拟岛”还是“真机”。

网页按研究人员要做的事组织成两个页面（2026-11-18 用户要求重构，原来的 7 个页面合并进来，内容要求不变）：

| 页面 | 内容 |
|---|---|
| 实验岛 | ① 需要您处理：待审阅的方案、待回答的提问，各带去处理的链接。② 冻结时：说明（原因、时间、中断的是哪个方案第几步、哪条设备指令），和结论表单：这一步已经完成 / 这一步没有完成 / 终止实验；那一步是搬运时，还要选那块板现在在哪，不选不能提交。③ 正在执行的方案：进度和当前步骤。④ 台面与器皿：各位置上是哪块板、板里装了什么；放上（编号、类型、位置、内容）、改内容、更正位置、取走。位置用下拉框，只列现场配置里能放器皿且空着的位置，显示编码（如“料架 1-2”），不用自然语言描述；内容是一张小表（名称、孔位、体积，可留空）；选项只给账本能接受的；P8 接入时加各孔初始物料与枪头盒余量录入/导入。⑤ 设备：各设备关键读数（中文名、单位、取值含义）、状态是否新鲜、设备报错；P8 接入时加每孔体积/成分与枪头余量查看及人工更正 |
| 任务 | 左边：全部任务（含历史），标出待审阅、待回答；“新建任务”写目标或 SOP。右边是一项任务：阶段条（提出要求 → 方案 → 执行 → 报告）和四个视图，默认打开现在需要人做事的那个。**对话**：研究要求、协调者的提问和回答框、给 Agent 留言、过程里程碑、计划（`plan.md`）。**方案**：每一步和预演用时（PCR 程序画成阶段卡片）、预演结论、孔板去向；“执行前现场应该是这样”逐项勾选，填批准人名字，全部勾选且有名字才能批准；退回必须写意见；P8 接入时加关键孔板、起始孔位与枪头盒核对。**执行**：进度、当前步骤、等待最多还剩多久、预计还需多久；暂停 / 继续 / 全部停止 / 终止实验（停止和终止要再确认一次），并写明第 5.15 节的停止限制。**报告**：`report.md`（可下载）、批准与退回记录、本任务用到的孔板的经历 |

全站共用的部分：

| 部分 | 规定 |
|---|---|
| 顶部状态条 | 网关是否在线、服务是否还在更新状态（心跳超过 10 秒没更新就提示）、是否冻结、正在执行的方案和步数。每 2 秒读一次数据库；服务记下新事件、处理完一条命令或冻结状态变化时，整页刷新 |

## 9. 评测（第一阶段不开发）

### 9.1 现在的结构已经保证的

| 评测需要 | 现在由什么保证 |
|---|---|
| 实验岛不依赖我们的 Agent | 第 3 节决定 1 |
| 虚拟岛可复位、可复现 | 场景是数据；确定性 |
| 按最终状态打分，答案对被测方隔离 | 虚拟后端的真相账，Agent 读不到 |
| 参考解 | 方案文件可由程序直接执行 |
| 外部 Agent 逐步调用工具 | 调用技能的入口是 `registry.call`，不依赖方案；`operations` 表的方案编号可空。“谁可以直接调动作技能”是每座实验岛的一项配置：真机只有服务，评测用的虚拟岛可以开放给被测 Agent |
| 工具可通过 MCP 提供给外部 Agent | `registry.catalog()` |
| 完整轨迹 | 对话记录加 `operations` 表，带模型名、代码版本、工具目录版本 |
| 区分 Agent 的问题和设备的问题 | 返回状态是线索，不是结论。`blocked` 是 Agent 的问题；`unknown` 是基础设施的问题；`failed` 两种都可能：设备自己出故障，或 Agent 的做法导致失败（如程序被提前停止、以后移液参数不当引起堵塞）。`failed` 带具体的错误码；评测时还要用参考解在同样条件下跑一遍做对照 |

### 9.2 做评测之前必须先回答的问题

这些是 2026-11-18 独立审查提出的。现在不开发，先记录，做评测时逐条回答（第 15.2 节）：

| 问题 | 说明 |
|---|---|
| 真机的吞吐量有限 | 一座岛、任务按小时到天计、每个任务还要重复几次。用户的意见：单座真机可以接受。审查的建议（真机只做少量终审，大规模比较靠虚拟岛或数据回放）记录在此，做评测时再定 |
| 虚拟岛现在只做符号记账 | 它检查比例、温度、枪头，不模拟蒸发、混匀、挂壁残留。一份在真实实验里会失败的方案，在虚拟岛上可以拿满分。虚拟岛的分数能说明“工具用得对不对”，不能说明“实验做得成不成” |
| 人工批准和客观评测冲突 | 评测时人退回并写意见，测到的是人和 Agent 合在一起的成绩。评测模式要另定规则（如预演不过直接判零分，不给修改意见） |
| 前后两次真机实验互相影响 | 试剂放置时间、批次、上一个被测系统留下的污染 |
| 测什么 | 现在的任务（照 SOP 换算体积、排步骤）考的是工具使用和算术，不是科学判断 |
| 一次实验内部的闭环 | 现在根据结果做选择只能发生在两个实验之间（两份方案之间）。有了读数之后，有些调整必须在一次实验内部几分钟内完成。线性方案加人工批准做不到，届时需要自动批准或方案里允许“用上一步的读数算下一步的参数” |

## 12. 代码规则

1. **内部代码不写防御性分支。** 检查只写在三处：技能的参数范围、互锁（`safety.py` 和各设备的 `rules.py`）、器皿账本。其余代码默认传进来的数据是对的。
2. **从外面进来的东西按它实际会出现的全部格式处理。** “外面”指：MQTT 报文、模型的输出（包括 Agent 写进 `commands` 表的命令）、模型接口的报错、人在界面上填的内容。已知的格式（包括抓包里见过的各种失败格式）都要认得；认不出的报文存档、计数，不让接收线程退出。这不算防御性代码：这些格式是实测到的事实。
3. 不吞异常。技能直线写；异常在 `registry.call` 一处转成返回格式；意料之外的异常在服务循环一处处理：冻结并写事件。出错后把设备收回安全状态再把异常原样抛出（如关热盖，`try … finally`）不算吞异常。
4. 不重试设备指令。全系统唯一的自动重试是模型接口调用和 MQTT 断线重连，都用库自带的。
5. 上层代码不出现“如果是虚拟”的判断。
6. 一样东西只定义一次：设备的一切在它自己的文件夹里，表结构在 `migrations/`，计划在协调者的待办清单里，其余都是生成的。
7. `lab` 不引用大模型库；包之间的依赖按第 5.2 节，由 import-linter 检查。
8. 一个文件只管一件事，超过约 300 行就拆。
9. 不做临时版本。“以后”的东西只在本文里留位置，不写代码。
10. 能用成熟的库就不自己写（SimPy、paho-mqtt、pydantic、SQLite、LangChain 中间件和 `init_chat_model`、Streamlit、import-linter）。用之前对照已安装版本的源码确认它有这个功能。
11. 一行只做一件事。不把几个赋值或几条语句挤在一行，一行不超过 100 个字符。文件太长就拆文件，不压行。
