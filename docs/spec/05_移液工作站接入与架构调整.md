## 1. 目标

### 1.1 为什么做

用户的判断：决定生物实验成败的是操作细节（体积怎么定、吸前要不要先吸一段空气、吸完要不要再多吸一段空气、速度、高度、靠壁、换不换枪头），不是“从 A 转到 B”。所以移液工作站上的**所有细节操作都要由 Agent 调用**。这也是以后评测真正要比的东西。

### 1.2 本阶段做完是什么样

| # | 结果 |
|---|---|
| 1 | 虚拟岛上：研究人员写“把 A1 里的水分 50 µL 到 B1～B3”，Agent 出一份原子级的方案（每次装枪头、吸、排、吹出都写明参数），预演通过，人批准，服务在虚拟 Flex 上执行，账本里每孔体积和枪头用量正确，出报告 |
| 2 | 真机上：同一份方案在 Flex 上执行（装水），结果和虚拟岛一致 |
| 3 | 结构上：一座岛同时有 GW_001 的设备和 Flex，互锁、冻结、全部停止、重启对账都覆盖 Flex |

不在本阶段：机械臂和 Flex 之间搬板；task.md 全程；读板测量闭环（等模块配置确定，第 10 节“之后”）。

## 2. 已定的决定

| # | 决定 | 理由 |
|---|---|---|
| 1 | **Flex 由我们的服务直接连接（HTTP），不经厂商网关** | 用户决定（2026-11-18）。P8 的先例：厂商驱动只包了一部分功能，单步吸排的细节没有包进去 |
| 2 | **一座岛可以有多个后端**，按设备所属的“连接”分发指令：GW_001（MQTT）一个，Flex（HTTP）一个 | 决定 1 的直接结果。取代 04 决定 3 的“一个后端” |
| 3 | **真机 Flex 和虚拟 Flex 用同一份后端代码，只有地址不同**。虚拟 Flex 是 Opentrons 自己的服务端在模拟硬件下运行，我们不为 Flex 写虚拟模型 | 能用成熟的就不自己写；同一份代码，虚实差别最小（04 决定 2） |
| 4 | **工具层级 = 写 Opentrons 程序时用的单条命令**：装枪头、吸、排、吹出、空气隔断、靠壁、移到孔位、液面探测等。不做组合函数（`transfer`、`distribute`、`consolidate`、`mix`、按液体类的转移），不做坐标和电机级 | 用户决定（2026-11-18）。组合函数会替 Agent 决定换不换枪头、怎么拆体积、用什么默认参数 |
| 5 | **技能的参数全部必填，我们不代填默认值**。Opentrons 官方液体类（水、50% 甘油、80% 乙醇）的参数只作为参考资料给 Agent 读 | 记录完整、能原样重跑、评测时能比较不同模型选了什么 |
| 6 | **检查只拦“物理上做不到”和“物料上不成立”**；科学上的选择（吹不吹出、快还是慢、换不换枪头）不拦，完整记录 | 这些正是要 Agent 判断的。拦了就等于我们替它做了决定 |
| 7 | **每孔体积、成分和枪头由我们的数据库记账，是唯一的真相**。Opentrons 引擎里的液体记录由我们在会话开始时按账本写入 | 调研实测：引擎的体积记录不设上下限（吸空了变负数也不报错），而且换一个 run 就丢了 |
| 8 | 方案仍然是一串展开的步骤，没有循环和条件（04 第 5.9 节）。新增可选的 `group` 字段，只用于给人看时折叠显示 | 每一步都单独检查、单独记录。一块板几百步是正常的 |
| 9 | 执行方式：服务在 Flex 上开一个 run，**一个技能发一条命令，等结果，再发下一条** | 每一步之前都能做我们的互锁（含跨设备的），每一步都有记录，结果不明时能冻结 |
| 10 | Flex 的状态用轮询（每秒），不用它机器上的 MQTT 通知 | 它的通知里没有数据，只是叫你重新读；每秒一轮的服务循环用轮询就够了，少一条连接 |
| 11 | 器皿几何（孔深、孔径、容量）用 Opentrons 的器皿定义（`opentrons-shared-data` 包，或自定义器皿 JSON）；**死体积和有效工作体积由现场配置给出** | 器皿定义里没有死体积；这个数要生物同事给 |
| 12 | Flex 会动的命令报失败，一律按“结果不明”冻结 | 和 04 第 16.6 节第 31 项一致。例如吸液时过压报错，枪头里有多少液体不知道 |
| 13 | P8 不在本阶段。04 第 7 节的摸底照旧，不写代码。第 5 节的工具规则以后接 P8 时照用 | 用户：以后更多在 Opentrons 上开发 |

## 3. 调研结论（2026-11-18）

“实测”是调研时在电脑上跑 `opentrons` 10.1.0 得到的；“源码”是读 GitHub `edge` 分支得到的，可能比已发布版本新；“待验证”的在第 10 节步骤 0 或到货后确认。

| 方面 | 结论 | 状态 |
|---|---|---|
| 版本 | Python 接口最新 2.30，对应机器软件 10.0.0。Flex 支持 2.15～2.30；OT-2 只到 2.28，软件线已分开 | 官方文档 |
| 命令级粒度 | HTTP 命令有 `pickUpTip`、`dropTip`、`aspirate`（`flowRate` µL/s、`correctionVolume`）、`dispense`（`pushOut`）、`blowout`、`airGapInPlace`、`touchTip`、`moveToWell`（`speed`）、`liquidProbe`、`tryLiquidProbe`，以及 `aspirateInPlace` 等“原地”版本。位置用 `wellLocation`：相对孔顶、孔底、中心或液面，加偏移 | 源码 |
| Python 层才有的 | `mix`、`transfer`、按液体类的转移是 Python 层的组合，命令层没有，要用原子命令拼。下降、提升速度可以用 `moveToWell` 的 `speed` 加“原地”吸排拼出来 | 源码，推断 |
| 只在 Flex 上有 | 液面探测、液体类、吸液时跟随液面、夹爪、出错恢复、吸光度读板模块、内置相机 | 官方文档 |
| 一条一条发命令 | `POST /runs/{id}/commands`，可以 `waitUntilComplete`；超时后命令不会被取消，可以按命令编号再查。`intent=setup` 在 run 空闲时立即执行；`intent=protocol` 要 `play` 之后才执行。**官方没有“外部程序逐条发命令跑完整流程”的说明和例子** | 源码；长时间运行待验证 |
| 状态 | 门、急停、移液器、模块、当前 run 的状态都能读；枪头有没有装上在 `currentState` 里（实验性接口） | 源码 |
| 暂停、停止 | `pause` 在当前运动结束后生效；`stop` 打断当前命令，之后这个 run 不能再用，收尾时默认退掉枪头并回零 | 源码 |
| 防重复 | 没有幂等保护。命令有 `key` 字段，可能能放我们的操作编号 | `key` 待验证 |
| 权限 | 本地 HTTP 接口没有鉴权；同一时间只有一个当前 run，别人占着时返回 409 | 源码 |
| 仿真能拦的 | 没装枪头就吸、超出枪头容量、枪头用完、孔不存在、槽位已占、排得比吸得多、部分模块的台面冲突 | 实测 |
| 仿真拦不住的 | 从空孔吸液（体积变负数）、排液溢出、低于最小移液量、伸到孔底以下、8 通道伸进窄槽、一般性的碰撞 | 实测 |
| 虚拟机器人 | 服务端源码里有开发模式，用模拟硬件在本机起一个和真机接口一样的服务（端口 31950），运动瞬间完成 | 源码；没实际跑过，待验证 |
| 先例 | Coscientist、Opentrons 官方的 AI 程序生成器、几个开源评测，都是让模型写整份 Python 程序再仿真；PyLabRobot 用 HTTP 逐条发命令，但只支持 OT-2、单通道 | 论文、源码 |
| 和外部机械臂交接 | 外部放进来的板怎么登记，没有官方说明；Flex 开门会让 run 暂停；没找到和第三方机械臂集成的官方案例 | 待到货后现场定 |

调研全文没有存进仓库；需要时以官方文档 https://docs.opentrons.com 和源码 https://github.com/Opentrons/opentrons 为准。

## 4. 总体结构

```
   界面进程                 Agent 进程
   读库；写 commands        读 events；写 commands
            └──────────┬──────────┘
                       ▼
            这座岛的数据库（SQLite）
                       ▲
┌─ 服务进程 ─────────────┴──────────────────────────────────────────┐
│  service → protocol → registry → lab（冻结 → 互锁 → 发送 → 核对 → 记录）│
│                                     │                               │
│                            IslandBackend（按设备的连接分发）           │
│                     ┌───────────────┴────────────────┐              │
│              连接 GW_001                         连接 flex            │
│         真机：MqttBackend                 真机：OpentronsBackend（真 Flex 地址）│
│         虚拟：SimBackend                  虚拟：OpentronsBackend（虚拟 Flex 地址）│
└──────────────────────────────────────────────────────────────────┘
                                                     │ HTTP
                                    真 Flex，或本机上运行的虚拟 Flex（Opentrons 服务端）
```

04 第 4 节的四条总规则，第 3 条改为：

> 真实和虚拟的差别只存在于 `lab/mqtt/`、`lab/sim/`、各设备的 `sim.py`，以及 Flex 的地址。`lab/opentrons/` 对真机和虚拟 Flex 是同一份代码。

其余三条不变：`lab` 不引用 `agents`、`app` 和任何大模型库；只有服务进程持有后端；后端以上一律用设备短名（Flex 的短名是 `flex`）。

## 5. 移液设备的工具怎么包装

本节的规则适用于所有移液工作站：现在的 Flex，以后的 P8 或别的型号。

### 5.1 层级

| | 机械臂（对照） | 移液工作站 |
|---|---|---|
| 给 Agent 的工具 | `transfer(板, 目标位置)` | 设备编程接口里的单条命令，参数全部开放 |
| 不给的更细一级 | 坐标、关节运动 | 坐标运动、电机轴运动、校准、设置 |
| 不给的更粗一级 | — | 组合函数（转移、分配、合并、混匀、按液体类的转移）。需要时由 Agent 在方案里用单条命令拼出来 |

每台设备按它自己的原子动作给工具，不在上面另做一层统一的移液接口。不同设备的原子动作划分不一样（例如 P8 的吹出是吸液参数里的“前吸空气”加排液的“排空模式”，Flex 是单独的 `blowout` 命令），这些差别本身就是影响结果的细节。

### 5.2 Flex 的第一批技能

一个技能对应一条 Flex 命令。名字用 `flex_` 开头，参数名跟着 Opentrons 命令走（改成蛇形写法并带单位），这样 Opentrons 的文档对 Agent 直接有用。

| 技能 | Flex 命令 | 说明 |
|---|---|---|
| `flex_pick_up_tip` | `pickUpTip` | 指定枪头盒和孔位，不用自动取 |
| `flex_drop_tip` | `dropTip` | 退到指定位置（枪头盒原位或垃圾桶） |
| `flex_aspirate` / `flex_aspirate_in_place` | `aspirate` / `aspirateInPlace` | |
| `flex_dispense` / `flex_dispense_in_place` | `dispense` / `dispenseInPlace` | 含 `push_out_ul` |
| `flex_blow_out` / `flex_blow_out_in_place` | `blowout` / `blowOutInPlace` | |
| `flex_air_gap_in_place` | `airGapInPlace` | |
| `flex_touch_tip` | `touchTip` | |
| `flex_move_to_well` | `moveToWell` | 含 `speed_mm_s`，用来控制下降和提升速度 |
| `flex_move_to_trash` | `moveToAddressableArea` | 只允许垃圾桶、废料槽这类有名字的位置 |
| `flex_probe_liquid` | `tryLiquidProbe` | 返回液面高度或“没探到”，不当作失败 |
| `flex_configure_for_volume` | `configureForVolume` | 50 µL 移液器的低体积模式 |
| `flex_configure_nozzles` | `configureNozzleLayout` | 部分取枪 |
| `flex_home` | `home` | |
| `flex_status` | 读状态 | 只读 |
| 模块类（按到货配置增减） | `heaterShaker/*`、`temperatureModule/*`、`thermocycler/*`、`absorbanceReader/*`、夹爪 `moveLabware` | 长时间的升降温沿用 04 第 5.15 节：启动后立即返回 → `wait_until` → 确认 → 收尾 |

`mix` 没有对应的命令，由 Agent 用吸、排交替拼出来。

### 5.3 参数的写法

```json
{"skill": "flex_aspirate",
 "args": {"pipette": "left", "labware_id": "LW-003", "well": "A1",
          "origin": "bottom", "offset_mm": {"x": 0, "y": 0, "z": 1.5},
          "volume_ul": 50, "flow_rate_ul_s": 20},
 "group": "A1 的水 50 µL 转到 B1"}
```

| 规定 | 内容 |
|---|---|
| 参数全部必填 | 包括流速、高度、偏移（决定 5） |
| 器皿用我们的编号 | `labware_id` 就是账本里的编号。会话开始时用这个编号作为 Opentrons 里的 `labwareId` 加载器皿（第 6.2 节），两边一致，不用转换表 |
| 移液器用安装位置 | `left`、`right`（96 通道用 `left`），对应现场配置 |
| 位置 | `origin` 取 `top`、`bottom`、`center`、`meniscus`，再加 `offset_mm`。`meniscus` 要求 Opentrons 知道液面高度，由我们按账本写入（决定 7） |
| 技能内部 | 账本检查（第 5.4 节）→ `lab.do("flex", 命令, 参数)` → 成功后更新账本 → 记录。直线写，不处理异常（04 第 12 节） |

### 5.4 检查：拦什么，不拦什么

| 类别 | 例子 | 在哪里拦 |
|---|---|---|
| 物理上做不到 | 吸液量加上前后空气超过枪头容量；低于移液器或枪头的最小量；位置低于孔底；8 通道伸进单孔太窄的器皿；孔位不存在 | `devices/flex/rules.py`，依据器皿几何和移液器参数 |
| 物料上不成立 | 源孔可吸体积不够（扣掉死体积后）；排完超过有效工作体积；枪头用完；用的枪头已经用过；没装枪头就吸 | 孔级账本（第 6.4 节） |
| 引擎自己会拦的 | 没装枪头、超容量、槽位冲突等（第 3 节） | Opentrons 引擎。我们照样先查，引擎是第二道 |
| 不拦，只记录 | 吹不吹出、快还是慢、高度选得好不好、要不要换枪头、要不要靠壁 | — |

最后一类的对错只能靠测量来判断（第 10 节“之后”的读板测量）。

### 5.5 方案和给人看的样子

方案格式不变（04 第 5.9 节），技能步骤多一个可选的 `group` 字符串。`render.py` 把同一组的连续步骤折叠成一行：

```
A1 的水 50 µL 转到 B1（6 步）：新枪头 → 孔底上 1.5 mm 以 20 µL/s 吸 50 µL → … → 退到垃圾桶
```

展开后能看到每一步的全部参数。和液体类参考值不一样的参数，在展开时标出来，方便人核对。

## 6. 实验岛的改动

### 6.1 一座岛多个后端

| 改动 | 内容 |
|---|---|
| 设备声明连接 | 各设备 `spec.py` 加 `LINK`：现有 5 台是 `"GW_001"`，Flex 是 `"flex"`。`gateway/spec.py` 的内置动作属于 `GW_001` |
| `IslandBackend` | 新文件 `lab/island_backend.py`。构造时传入 `{连接名: 后端}`，`call` 按设备的 `LINK` 分给对应后端；`state` 合并各后端的状态表；`closed_skills` 取并集；`now`、`sleep` 用 `GW_001` 那个后端的时钟（真机是系统时间，虚拟岛是虚拟时钟）。它只引用 `devices` 和 `backend`，放在依赖层的第 ④ 层 |
| 状态表里的连接 | `_gateway` 改为 `_links: {"GW_001": {"online", "busy_by_others"}, "flex": {"online", "busy_by_others"}}`。`Lab.state()` 原样转出 |
| 互锁第 3、4 条 | 看目标设备**自己那条连接**是否在线、是否被别人占着；“岛上任一设备 `WorkingStatus=1`”改为“同一条连接上的设备”。原因：GW_001 逐条处理指令，Flex 和它互不排队 |
| 服务、对账、`doctor` | 按连接分别判断在线、分别冻结和写事件。`gateway_was_online` 改为每条连接一个 |

为什么要多这一层：岛上第一次有两条物理连接，总得有一处知道哪台设备走哪条。放在后端这里，`Lab`、`safety` 以上的代码都不用知道有几条连接。

### 6.2 Opentrons 后端（`lab/opentrons/`，真机和虚拟 Flex 共用）

| 文件 | 内容 |
|---|---|
| `client.py` | HTTP 客户端（httpx），带 `Opentrons-Version` 头。每个请求和应答追加到这座岛 `raw/` 下按日期分的文件，和 MQTT 一样 |
| `session.py` | Flex 会话：服务在 Flex 上开一个 run，编号存数据库。开 run 后按账本加载移液器、模块、台面上的器皿（`labwareId` 用我们的编号）、各孔的液体。run 丢了（机器重启、停止之后）就新开一个，按账本重新加载 |
| `state.py` | 每秒读一次：run 状态、当前命令、门、急停、移液器和枪头、模块。整理成状态表，`_age_s` 按读取时间算。当前 run 不是我们开的 → `_links.flex.busy_by_others=true` |
| `backend.py` | `OpentronsBackend(url)`：实现后端接口。`call` 只发一次命令，`waitUntilComplete` 等结果；等待超时后按命令编号继续查，直到命令结束或到了上限才抛 `NoResult`，**不重发**。命令失败 → `DeviceFailed`，带 Opentrons 的错误类型和说明。`closed_skills`：真机初始包含全部动作类的 Flex 技能，陪同首跑通过一个删一个（同 04） |

用 `setup` 还是 `protocol` 方式发命令、`key` 能不能带我们的操作编号、长时间开着的 run 稳不稳，由步骤 0 实测决定，结论写回本节。

### 6.3 Flex 设备文件夹和现场配置

```
  rules.py    第 5.4 节“物理上做不到”的规则；fault（run 失败、急停、等待恢复）；ready_for_arm（以后搬板用）
```

### 6.5 预演

`rehearse.py` 现在用“虚拟后端 + 内存数据库”。加了 Flex 之后：GW_001 的设备照旧用 SimBackend；Flex 用一台**专门给预演用的虚拟 Flex**（和虚拟岛用的那台分开，端口不同）。每次预演新开一个 run，按快照加载，然后逐步执行。

| 规定 | 内容 |
|---|---|
| 同一时间只做一次预演 | Agent 进程和界面进程都可能发起预演，用文件锁排队 |
| 耗时 | 虚拟 Flex 的动作瞬间完成。预演报告里 Flex 各步的耗时用真机首跑的实测值校准；校准之前标为“未校准” |
| 拦下的理由 | 我们的检查（第 5.4 节）和 Opentrons 引擎的报错都写进“第几步、为什么、当时的状态” |

### 6.6 服务

| 环节 | 内容 |
|---|---|
| 启动核对 | 读 Flex 的版本、移液器、模块、台面配置，和 `island/flex/robot.json` 对比，不一致就冻结并写明（同 04 第 16.6 节第 34 项） |
| 全部停止 | 包含 Flex：对我们的 run 发 `stop`。注意 Opentrons 停止后会自己退掉枪头并回零，枪头账本要据此更新。停止在冻结时也放行（04 决定 22） |
| 暂停 | 不再发新步骤即可。Flex 的单条命令都短（液面探测最长约 50 秒），不用 Opentrons 自己的暂停 |
| 重启对账 | 我们的服务重启：找回 Flex 上的 run 继续用。Flex 重启或 run 丢失：新开 run，按账本加载；移液器上还挂着枪头、或者某一步是 `sent` → 冻结等人 |

## 10. 开发步骤

```

                    └→ 3（Flex 设备文件夹）──┤
04 阶段 1 合并 → 1（多后端）────────────────┴→ 4（孔级账本）→ 5（预演）→ 6（服务）→ 7（Agent 和界面）→ 8（真机）
```

每一步都要有测试，长期保留；测试里需要 Flex 的，连本机的虚拟 Flex。

### 步骤 0：在电脑上验证（不写产品代码，不碰真机）

在本机起虚拟 Flex，逐项实测，结论写回本文第 3、6.2、7 节：

| # | 要弄清的 |
|---|---|
| 1 | 虚拟 Flex 怎么起最省事（源码开发模式还是容器）；启动要多久；能不能在两个端口同时起两台 |
| 2 | 一个 run 里用 `setup` 方式逐条发命令：连续 2 小时、中间空闲 30 分钟后还能不能用；`protocol` 方式加 `play` 之后，队列空了 run 会不会自己结束。选定一种 |
| 3 | 命令的 `key` 能不能放我们的操作编号，查询时原样返回；`loadLabware` 能不能用我们的器皿编号作 `labwareId`；移液器能不能指定编号 |
| 4 | 每孔体积怎么写进引擎（让 `meniscus` 位置能用）；指定孔位取一个“已用过”的枪头会不会被拒 |
| 5 | 命令等待超时后按编号查结果；`stop` 打断正在执行的命令；`stop` 之后新开 run 并重新加载 |
| 6 | run 中途加载新器皿、把器皿移出台面（模拟人或机械臂放板、取板）怎么做 |
| 7 | 一条命令失败后 run 的状态：还能不能接着发；出错恢复对逐条发的命令生不生效 |
| 8 | `opentrons-shared-data` 能不能装进我们的环境（Python 3.11），读出器皿几何和官方液体类 |
| 9 | 液面探测在虚拟 Flex 里返回什么 |

做完的标准：每一项有结论和证据（命令、返回）；能定下第 6.2 节的发送方式和第 7 节的启动方式。

### 步骤 1：多后端（04 阶段 1 合并之后）
